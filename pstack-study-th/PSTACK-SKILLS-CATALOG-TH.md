## หมวด A: ตัว Router และ Workflow หลัก

### `poteto-mode`
**ทำอะไร:** เป็นตัว router และกรอบการทำงานหลักของ pstack รับงานแล้วเลือก playbook ที่เหมาะ จากนั้นเปิด todolist ตามขั้นตอน มอบงานให้ subagent ตรวจผล และเขียนคำตอบตามมาตรฐาน

**เหมาะกับ**
- งานที่แตะมากกว่าหนึ่งไฟล์ หรือเปลี่ยน signature ที่ไฟล์อื่นเรียกใช้
- งานที่ต้องตัดสินใจเชิงออกแบบหรือสถาปัตยกรรม
- บั๊กที่ยังไม่รู้สาเหตุ หรือปัญหา performance
- เมื่อไม่แน่ใจว่าควรใช้ skill ไหน

**ไม่เหมาะกับ:** แก้ไฟล์เดียวที่มี test ชัด, คำถามสั้น ๆ, แก้บรรทัดเดียว (hook บอกให้ทำตรง ๆ)

**สิ่งที่อยู่ข้างใน**
- **Non-negotiables:** กฎแบบ "สถานการณ์ → skill ที่ต้องใช้" เช่น ก่อน commit ต้องใช้ `deslop` ก่อนรีวิวต้องใช้ `no-comments`
- **Principles index:** ดัชนี principle ทั้งหมดพร้อมเงื่อนไขว่าใช้เมื่อไร
- **Autonomy:** งานที่ย้อนกลับได้ทำเลย ส่วน force-push, deploy และลบข้อมูลต้องหยุดถาม
- **Subagents:** ใช้ `pstack:poteto-agent`, รันเบื้องหลัง และเริ่ม agent ตัวใหม่ทุกครั้งที่มีงานใหม่
- **Playbooks:** 23 แบบ (ดูภาคผนวก)

**ตัวอย่างการใช้:** `Use poteto-mode to fix the search filter resetting when I change pages.`

---

### `figure-it-out`
**ทำอะไร:** ออกแบบ playbook ใหม่สำหรับงานที่ไม่มี playbook ไหนเข้ากัน ผลลัพธ์แรกคือ workflow ที่คนตรวจได้ ยังไม่ใช่โค้ด

**เหมาะกับ**
- migration ใหญ่ที่แตะหลายจุด
- การเปลี่ยนแปลงหลายส่วนที่ซับซ้อน
- งานที่ผู้ใช้จะทิ้งไว้แล้วกลับมาตรวจทีหลัง
- งานที่ไม่ตรงกับ playbook ใดเลย

**ไม่เหมาะกับ:** โปรเจกต์หลายวันที่มี PR ซ้อนกันจำนวนมาก (ใช้ playbook Orchestrate) และงานเล็กที่มี playbook รองรับอยู่แล้ว

**ขั้นตอน**
1. **Frame:** เขียน definition of done ให้เป็นเงื่อนไขที่พิสูจน์ได้, ประมาณขนาดงาน และเลือกระดับความเข้มงวด
2. **Design:** แตกงานเป็นหน่วยย่อย ทำส่วนที่เสี่ยงที่สุดก่อน และสร้าง harness สำหรับ verify ก่อนเริ่มงานจริง
3. **Loop:** แต่ละหน่วยถือเป็นการทดลอง ตั้งสมมติฐาน → แก้ให้น้อยที่สุด → วัดผล → เก็บไว้หรือ revert
4. **Audit trail:** บันทึกการตัดสินใจด้วย `show-me-your-work`
5. **Verify:** ตรวจกับของจริง แล้วเปลี่ยนความผิดพลาดที่เกิดซ้ำให้เป็น gate

**ผลลัพธ์:** playbook ที่ออกแบบ, ระดับความเข้มงวดพร้อมเหตุผล, path ของ decision trail, สิ่งที่ verify แล้ว และสิ่งที่ยังค้าง

## หมวด B: ทำความเข้าใจโค้ดและบริบท

### `how`
**ทำอะไร:** อธิบายว่าระบบส่วนหนึ่งทำงานอย่างไร ในระดับที่วิศวกรอาวุโสใช้ปูพื้นให้คนที่เพิ่งเข้าทีม

**เหมาะกับ**
- คำถามแบบ "X ทำงานอย่างไร"
- ไล่โค้ดก่อนจะแก้
- คำถามเรื่องตำแหน่งและเจ้าของโค้ด เช่น "ควรวางไว้ที่ไหน", "package ไหนเป็นเจ้าของ", "อยู่ layer ถูกไหม"
- เรียนรู้ระบบใหม่

**ไม่เหมาะกับ:** คำถามว่า "ทำไม" ให้ใช้ `why`

**ขั้นตอน**
1. ประเมินความซับซ้อน ถ้าไม่แน่ใจให้เลือกแบบง่าย
2. งานง่าย: ใช้ explainer ตัวเดียว สำรวจและอธิบายในรอบเดียว
3. งานซับซ้อน: แบ่งเป็น 2-4 มุม ส่ง explorer แบบอ่านอย่างเดียวไปพร้อมกัน แล้วให้ explainer สังเคราะห์
4. นำเสนอผล แก้ภาษาได้เล็กน้อย แต่ห้ามเขียนใหม่

**ผลลัพธ์:** Overview / Key Concepts / How It Works / Where Things Live / Gotchas

---

### `why`
**ทำอะไร:** สืบหาเหตุผลเบื้องหลังโค้ด ว่าทำไมถึงออกแบบแบบนี้ เลือก Y เพราะอะไร หรือ regression มาจากไหน โดยค้นหลักฐานจากทุกแหล่งที่เชื่อมต่ออยู่

**เหมาะกับ**
- คำถาม "ทำไม X ถึงทำงานแบบนี้" หรือ "ทำไมเลือก Y"
- ตามหาที่มาของ regression หรือทำ postmortem
- หาที่มาของค่า threshold
- ก่อนแก้โค้ดที่ดูแปลก ๆ เพื่อไม่ให้ลบสิ่งที่มีเหตุผลรองรับ

**ไม่เหมาะกับ:** คำถามว่าโค้ดทำงานอย่างไรตอน runtime (ใช้ `how`)

**ขั้นตอน**
1. ทำความเข้าใจเป้าหมายและคำถาม
2. **Code anchor:** รวบรวม path, ช่วงบรรทัด, symbol, commit และ PR (`git blame`, `git log --follow`, `gh pr view`)
3. **ค้นหา MCP** ที่เชื่อมต่ออยู่ แล้วจับคู่กับหลักฐาน 7 ประเภท ได้แก่ source control, ticket, docs, chat, observability, error tracking และ analytics
4. ส่ง investigator ประเภทละหนึ่งตัวไปพร้อมกัน ถ้าข้ามประเภทไหนต้องเขียนเหตุผลไว้
5. Synthesizer รวมผลโดยแยกระดับความมั่นใจตามกรอบ `epistemics.md`
6. นำเสนอผล ห้ามแก้ภาษาที่บอกระดับความมั่นใจ

**ผลลัพธ์:** What We Found / Reasonably Infer / Competing Hypotheses / What We Don't Know / Sources Consulted / Confidence Summary ถ้าคำถามนำไปสู่การแก้โค้ด จะมีชุด Preserve / Change / Avoid / Risk ต่อท้าย

**จุดเด่น:** แหล่งที่ค้นแล้วไม่พบอะไรก็ต้องบันทึกไว้ เพราะนับเป็นหลักฐานอย่างหนึ่ง

### `teach`
**ทำอะไร:** สอนให้คนเข้าใจงานชิ้นหนึ่งจริง ๆ โดยเรียก `how` กับ `why` คู่ขนาน แล้วรวมผลเป็นคำอธิบายเดียวที่อ่านง่าย

**เหมาะกับ**
- "สอนผมเรื่องนี้หน่อย" หรือ "อยากเข้าใจ X จริง ๆ"
- อธิบาย change หรือ subsystem ให้คนที่จะรีวิว แก้ไข หรือเพิ่งเข้าทีม

**ไม่เหมาะกับ:** งานที่ต้องแก้โค้ด เพราะ teach ไม่เปลี่ยนอะไรเลย

**ขั้นตอน**
1. เลือกเรื่องไม่กี่ข้อที่ผู้ฟังควรเข้าใจ โดยดูจากเหตุผลที่ถามและสิ่งที่รู้อยู่แล้วในบทสนทนา
2. เรียก `how` และ `why` คู่ขนาน และใช้ `why` แบบแคบเป็นค่าเริ่มต้นเพราะช้า
3. เริ่มจากนิยามทั่วไปก่อน แล้วค่อยโยงเข้ากับเคสจริง
4. คุยแบบบทสนทนา ไม่ quiz ไม่เกริ่นว่า "ส่วนนี้ยาก"
5. ใช้ภาพประกอบ ถ้ามีส่วนประกอบ 3 ส่วนขึ้นไป ให้วาดเป็นชุดภาพที่ค่อย ๆ เพิ่มทีละส่วน

**ผลลัพธ์:** คำอธิบายโดยตรง ไม่ใช่รายงานว่าทำอะไรไปบ้าง

### `blast-radius`
**ทำอะไร:** หาว่าการเปลี่ยนแปลงจะทำให้อะไร **นอก diff** พังได้บ้าง และพิสูจน์ "ข้อเท็จจริงเดียวที่ทำให้ปลอดภัย" ด้วยการรันโค้ดจริง ไม่ใช่แค่เขียนวิเคราะห์

**เหมาะกับ**
- "blast radius ของ X" หรือ "แก้แล้วจะพังอะไรบ้าง"
- รีวิว diff เล็ก ๆ ที่ยังไม่ไว้ใจ
- brief ที่อ้างบางอย่างเกี่ยวกับโค้ดเดิม เช่น "ทำ endpoint X ให้ public" หรือ "X จัดการ Y อยู่แล้ว" ให้ใช้ก่อนออกแบบ เพราะคำอ้างนั้นเป็นแค่สมมติฐาน

**ระดับความมั่นใจ 5 ขั้น (จากอ่อนไปแข็ง)**
1. บอกว่าเป็นอย่างนั้น (ไม่มีค่าเลย)
2. ชี้ไปที่ `file:line`
3. ไล่ให้เห็นว่ากรณีเสียเกิดขึ้นไม่ได้
4. รัน script หรือ test ที่เรียกโค้ดจริง
5. reproduce ในแอปที่รันอยู่

**ขั้นตอน:** อ่าน change → หาข้อเท็จจริงเดียวที่ทำให้ปลอดภัย → ดูส่วนที่ grep มองไม่เห็น (source ของ library, จังหวะการทำงาน, JSON, คอลัมน์ใน DB, feature flag) → ประเมินแต่ละความเสี่ยงอย่างตรงไปตรงมา → พิสูจน์ด้วยการรันจริง → ถ้า change ใหญ่ ให้ใช้ `arena`

**ผลลัพธ์:** What it does / The one fact (ระบุว่าพิสูจน์แล้วหรือยัง) / Risks / Cleared / Before you merge

### `recall`
**ทำอะไร:** สร้างบริบทการทำงานล่าสุดของผู้ใช้ขึ้นมาใหม่ จากประวัติแชตและข้อมูลที่ทีมใช้ร่วมกัน (PR, ticket, incident) แล้วสรุปสั้น ๆ ว่างานอยู่ตรงไหน

**เหมาะกับ**
- "ผมทำอะไรค้างไว้", "catch me up" หรือ "recall my work on X"
- ก่อนเริ่มหรือกลับมาทำงานต่อ
- ก่อนบอกผู้ใช้ว่า "ไม่มีการบันทึกเรื่องนี้"

**ไม่เหมาะกับ:** รับช่วงงานจากแชตเดียวที่ระบุชัด (ใช้ playbook Session pickup) และการแปลงนิสัยการทำงานเป็น skill (ใช้ `automate-me`)

**ขั้นตอน**
1. แยกประเภทคำขอแล้ว route ให้ถูก
2. ล็อกขอบเขตก่อนค้น ค่าเริ่มต้นคือ 7 วันล่าสุดใน workspace ปัจจุบัน
3. ส่ง subagent ที่ใช้โมเดลเร็วไปค้นประวัติแชตคู่ขนาน
4. ค้นข้อมูลที่ทีมใช้ร่วมกันผ่าน investigator ของ `why` (ทำทุกครั้งที่หัวข้อระบุ feature หรือไฟล์)
5. ตรวจกับสถานะจริงด้วย `git` และ `gh`
6. เขียนสรุปตามรูปแบบที่กำหนด

**ผลลัพธ์**
- **Capsule:** ไม่เกิน 5 bullet
- **Threads:** หนึ่งบรรทัดต่อเรื่อง พร้อม tag เช่น `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[reverted #N]`
- **Problems:** ไม่เกิน 5 ข้อ
- **Next move:** สิ่งที่ควรทำต่อหนึ่งอย่าง

## หมวด C: ออกแบบและกระจายงานคู่ขนาน

### `architect`
**ทำอะไร:** ร่าง types, signatures และโครงสร้าง module ก่อนเขียนโค้ด แล้วใช้ร่างนั้นเป็น contract ระหว่าง implement

**เหมาะกับ**
- งานที่ไม่ง่าย ซึ่งถ้าเขียนโค้ดเลยอาจได้โครงสร้างที่ผิด
- โค้ดที่ข้าม function boundary
- "design this" หรือ "architect this"

**ไม่เหมาะกับ:** งานเชิงกลไกที่รู้รูปร่างชัดอยู่แล้ว (ถ้า architect ซ้ำทั้งที่ตัดสินใจไปแล้ว ถือว่าเกินจำเป็น)

**ขั้นตอน**
1. **Ground:** ใช้ `how` (และ `why` ถ้าเปลี่ยน ownership)
2. **Sketch:** ใช้ `arena` ให้หลายโมเดลร่าง โดยต้องได้อย่างน้อย 2 แบบที่โครงสร้างต่างกันจริง แล้วคัดทิ้งด้วย `design-red-flags.md`
3. **Agree:** ค่าเริ่มต้นคือไม่หยุดรอผู้ใช้ จะหยุดก็ต่อเมื่อผู้ใช้ขอ
4. **Implement:** เขียนตาม sketch ถ้าต้องเบี่ยงจาก sketch ต้องรายงานและอัปเดต sketch
5. **Scrap:** ถ้าเจอ workaround แบบเดิมซ้ำหลายที่ ให้ทิ้งแล้วออกแบบใหม่

**ผลลัพธ์:** ไฟล์ types และ signatures (หรือ module map ถ้างานใหญ่) พร้อม rationale

---

### `arena`
**ทำอะไร:** ให้ N candidate ทำงานเดียวกันคู่ขนาน เลือกชิ้นที่ดีที่สุดเป็นฐาน แล้วนำส่วนที่ดีของชิ้นอื่นมาเสริม

**เหมาะกับ**
- artifact ที่ไม่ง่าย ซึ่งถ้าทำครั้งเดียวอาจได้รูปแบบที่ผิด
- งาน implement ที่ทำได้หลายแบบที่ถูกต้องพอกัน (Feature playbook บังคับให้ใช้)
- "arena this" หรือ "throw it in the arena"

**ไม่เหมาะกับ:** งานที่มีคำตอบเดียวชัดเจน

**ขั้นตอน**
1. **Frame:** สร้าง rubric 3-6 ข้อ (candidate ไม่เห็น), เลือก runner (ค่าเริ่มต้นคือ opus, fable, sonnet) และกำหนด output path แยกให้แต่ละตัว
2. **Fan out:** ส่งทุกตัวพร้อมกันใน message เดียว แต่ละตัวต้องส่ง artifact และ rationale
3. **Cross-judge:** judge ที่ใช้โมเดลต่างตระกูลให้คะแนนตาม rubric
4. **Pick:** ตัวนำอ่านทุกชิ้นจนจบแล้วให้คะแนนทีละเกณฑ์
5. **Graft:** นำส่วนดีจากชิ้นอื่นมาเขียนใหม่ให้เข้ากับฐาน ถ้าผลต่างกันมาก ให้เขียนโจทย์ใหม่
6. **Verify**

**ผลลัพธ์:** artifact หนึ่งชิ้นพร้อม synthesis note

---

### `swarm`
**ทำอะไร:** ส่ง worker N ตัวทำงานคู่ขนาน แล้วรวมผลเป็นรายงานเดียว

**เหมาะกับ**
- **Coverage:** แบ่งงานเป็นชิ้น เช่น audit ทีละ module หรือทดสอบทีละ feature
- **Race:** หลายตัวแข่งทำ brief เดียวกัน
- **Gauntlet:** ตรวจหลาย commit หรือหลายเงื่อนไข
- การสำรวจหลายทิศทางพร้อมกัน

**ต่างจาก arena:** swarm เน้นความครอบคลุมและรวบรวมผล ส่วน arena เน้นเลือกชิ้นที่ดีที่สุดแล้วเสริมด้วยส่วนดีจากชิ้นอื่น

**ขั้นตอน**
1. **Frame:** กำหนด predicate, เลือกรูปแบบ (partition / race / mix) และกฎการเลือก (`first pass` / `rank all` / `best-of`)
2. **Fan out:** brief ทุกตัวต้องอ่านจบได้ในตัว ผลมีสถานะ `PASS` / `ISSUES` / `BLOCKED`
3. **Aggregate:** ผลที่ไม่มีหลักฐานจะถูก spawn ใหม่หนึ่งครั้ง ถ้ายังไม่มี ให้บันทึกเป็น gap ซึ่งไม่นับว่าผ่าน
4. **Report:** ส่งตารางผล ห้ามแปะผลดิบของ worker

## หมวด D: รีวิวและตรวจคุณภาพ

### `interrogate`
**ทำอะไร:** ให้ reviewer หลายโมเดลรีวิวโค้ดแบบตั้งใจหาจุดผิด โดยใช้ prompt เดียวกันทุกตัว

**เหมาะกับ**
- "adversarial review", "challenge this", "stress test", "find blind spots" หรือ "tear this apart"
- การออกแบบที่ยังมีข้อโต้แย้งก่อน ship
- รีวิว sketch จาก `architect` ก่อน implement

**ขั้นตอน:** กำหนดขอบเขต → เขียน intent หนึ่งย่อหน้า → ส่ง reviewer ไปพร้อมกัน → สังเคราะห์ (ปัญหาที่หลายโมเดลเจอตรงกันน่าเชื่อถือที่สุด) → ตัวนำตัดสิน

**ผลลัพธ์:** Intent / Reviewers / **Act On / Consider / Noted / Dismissed** / Agreement Map

**ข้อจำกัด:** ไม่แก้โค้ดอัตโนมัติ ผลลัพธ์คือ verdict เท่านั้น

### `thermo-nuclear-code-quality-review`
**ทำอะไร:** รีวิวคุณภาพโค้ดแบบเข้มงวดที่สุด เน้น maintainability, abstraction และการหาโอกาสปรับโครงสร้างครั้งใหญ่ (ที่ skill เรียกว่า "code judo")

**เหมาะกับ**
- deep code quality audit ของ branch
- โค้ดที่ทำงานได้ แต่รู้สึกว่ารก
- เมื่ออยากได้รีวิวที่โหดที่สุด

**กฎที่เข้มเป็นพิเศษ**
- หาทางปรับโครงสร้างที่ทำให้ branch, helper หรือ layer ทั้งก้อนหายไป
- **ห้าม PR ทำให้ไฟล์ที่ยาวไม่ถึง 1,000 บรรทัด กลายเป็นเกิน 1,000** ถ้าไม่มีเหตุผลที่หนักแน่นมาก
- ห้ามเพิ่ม if แบบเฉพาะกิจกระจายไปตามจุดต่าง ๆ ให้ย้ายไปไว้ใน abstraction, state machine หรือ policy object
- เอียงไปทางทำให้ design สะอาด ไม่ใช่แค่ยอมรับโค้ดที่ทำงานได้

**ต่างจาก interrogate:** interrogate ใช้หลายโมเดลหาบั๊กและจุดบอด ส่วน thermo-nuclear เน้นโครงสร้างและ maintainability อย่างเดียว

### `deslop`
**ทำอะไร:** เทียบ diff กับ main แล้วลบโค้ดขยะที่ AI ใส่เข้ามา

**สิ่งที่ลบ**
- comment ที่ไม่จำเป็นหรือไม่เข้ากับ style ของไฟล์
- defensive check หรือ try/catch ที่ผิดปกติสำหรับ code path ที่เชื่อถือได้
- cast เป็น `any` เพื่อเลี่ยง type error
- โค้ดซ้อนลึกที่ควรใช้ early return
- รูปแบบที่ไม่เข้ากับโค้ดรอบข้าง

**เหมาะกับ:** ก่อน commit ทุกครั้ง (poteto-mode บังคับ)
**กฎ:** ห้ามเปลี่ยนพฤติกรรม ยกเว้นแก้บั๊กที่ชัดเจน, แก้ให้น้อย และสรุปผล 1-3 ประโยค

### `no-comments`
**ทำอะไร:** ส่ง subagent `comment-sicko` ไปตรวจ comment ใน diff แล้วตัวนำเลือกว่าจะทำตามข้อไหน รวมถึงเสนอให้เปลี่ยน comment ที่เป็นข้อบังคับ (เช่น "do not remove") ให้เป็น type, test หรือ lint แทน

**เหมาะกับ:** ก่อนส่งรีวิว (poteto-mode บังคับ)

**Comment ที่ comment-sicko ยอมให้อยู่**
- license header
- พฤติกรรมแปลก ๆ ที่เกิดจาก dependency ภายนอกที่เราแก้ไม่ได้
- `// prettier-ignore`
- doc comment ของ public API
- ลิงก์ issue หรือ RFC ที่อธิบายข้อจำกัด

ถ้าโค้ดของเราเองมีพฤติกรรมแปลก จะถูกทำเครื่องหมาย `MUST KILL` ให้แก้โค้ดจนอ่านเข้าใจได้โดยไม่ต้องมี comment

**ขั้นตอน**
1. Spawn comment-sicko
2. ตรวจผลและปฏิเสธข้อที่เกินขอบเขต
3. แก้ข้อง่าย ๆ ทันที ข้อที่ต้องออกแบบให้ใช้ `architect`
4. แก้ที่ root cause
5. เสนอให้เปลี่ยน comment ที่เป็นข้อบังคับเป็นกลไก (รอผู้ใช้อนุมัติ)
6. รายงานผล

## หมวด E: ทดสอบและพิสูจน์ผล

### `tdd`
**ทำอะไร:** แก้บั๊กโดยเขียน test ที่ fail ก่อน แล้วค่อยแก้จน test ผ่าน

**เหมาะกับ**
- ผู้ใช้ขอ TDD, failing test หรือ regression test เอง
- บั๊กที่มีจุดให้เขียน test ได้ง่ายและถูก

**ไม่เหมาะกับ:** test ที่ต้องตั้ง harness ใหญ่, mock เปราะ, E2E ช้า หรือ state ที่มีเฉพาะใน production ถ้าเป็นแบบนั้นให้ใช้ script หรือ repro แทน **ไม่มี test ดีกว่ามี test ที่แย่**

**ขั้นตอน**
1. เข้าใจบั๊ก: พฤติกรรมที่ควรเป็นเทียบกับที่เป็นอยู่
2. เลือก check ที่แคบที่สุด
3. เขียน test ที่ fail
4. **รันก่อนแก้** และยืนยันว่า fail ด้วยเหตุผลที่ถูกต้อง โดยยกเนื้อหาความผิดพลาดมาแสดง
5. แก้ให้น้อยที่สุด
6. รัน test อีกครั้งและยืนยันว่าผ่าน

**ข้อห้าม:** ห้ามแก้ test ให้ตรงกับ implementation ที่ผิด และห้ามทำ assertion ให้อ่อนลง

---

### `benchmark-checklist`
**ทำอะไร:** ตรวจตัวเลข performance ก่อนนำไปรายงานหรือตัดสินใจ

**เหมาะกับ:** ทุกครั้งที่รัน benchmark หรือจะรายงานว่าเร็วขึ้นหรือช้าลง เช่น before/after ใน PR หรือการเลือก library

**ก่อนรัน:** เขียนประโยคที่จะใช้รายงานไว้ก่อน, อ่าน script ที่ใช้วัด และเช็ก `uptime` กับ `nproc`

**คำถาม 7 ข้อ**
1. **Why not double?** อะไรเป็นตัวจำกัด (profile ในรอบที่ไม่ได้ใช้รายงาน)
2. **Was it tuned?** ทุกฝั่งรันแบบ production หรือเปล่า
3. **Did it break limits?** คำนวณเทียบกับขีดจำกัดของ disk, network และ CPU
4. **Did it error?** นับ error และตรวจว่า output ถูกต้อง
5. **Does it reproduce?** รันอย่างน้อย 5 รอบสลับฝั่ง A/B แล้วรายงาน median และ range
6. **Does it matter?** วัด end-to-end ที่ผู้ใช้รอจริงด้วย
7. **Did it even happen?** งานถูกทำจริงในช่วงที่จับเวลาหรือเปล่า (ระวัง lazy code และ promise ที่ไม่มีใคร await)

**ผลลัพธ์:** verdict (faster / slower / no difference / inconclusive), ตัวเลขพร้อมหน่วย, จำนวนรอบ, range และตัวจำกัด

---

### `create-verification-skill`
**ทำอะไร:** สร้าง skill `verify` เฉพาะของโปรเจกต์ (`.claude/skills/verify/`) ให้ agent ขับแอปได้เหมือนผู้ใช้ และเก็บหลักฐาน รองรับทุกภาษาและแพลตฟอร์ม

**เหมาะกับ**
- โปรเจกต์ที่ยังไม่มีวิธีพิสูจน์พฤติกรรมของ UI, CLI หรือ service ด้วย script
- "make a driver skill for this repo"
- ก่อนเริ่มใช้ pstack จริงจัง เพราะหลาย playbook ต้องใช้ driver skill ในการ verify

**ขั้นตอน**
1. **สำรวจ repo ก่อนถามผู้ใช้:** Surface / Run / Drive / Observe / Isolate
2. **สร้าง skill:** แบ่งเป็นส่วน Launch / Doctor / Drive / Evidence / Cleanup / Helpers โดยใช้ selector และคำสั่งจริงจาก repo
3. **Seed feature map:** ไฟล์ละหนึ่ง feature เริ่มจาก 3-5 feature
4. **พิสูจน์ skill ที่สร้าง:** รันครบหนึ่งรอบ แล้วตรวจว่าหลักฐานยังอยู่หลัง cleanup
5. แนะนำ `maintain-verification-skill` สำหรับดูแลต่อ

### `maintain-verification-skill`
**ทำอะไร:** ดูแล skill verify และ feature map เป็นระยะ เพื่อให้ตรงกับแอปที่เปลี่ยนไป

**เหมาะกับ:** หลังแอปเปลี่ยนไปมาก, เมื่อสงสัยว่า verify skill ล้าสมัย หรือ "audit the verify skill"

**ขั้นตอน**
1. หา skill เป้าหมาย
2. ตรวจ index ของ feature map
3. **Source wave:** ส่ง subagent อ่าน source หนึ่งตัวต่อ feature
4. Reconcile ผล
5. **Live pass:** ขับทุก feature จริง ต้องทำแม้ source จะดูถูกต้อง
6. Triage เป็น doc drift / harness gap / product gap
7. Ship (PR เดียว) หรือหยุด

**ผลลัพธ์:** หนึ่งในสามแบบ คือ clean / changed / blocked
**ข้อห้าม:** ห้ามแก้โค้ดของผลิตภัณฑ์ ถ้าเจอบั๊กให้รายงาน

## หมวด F: งาน PR และ CI

### `babysit`
**ทำอะไร:** ดูแล PR ที่เปิดอยู่ แก้ CI ที่ fail จัดการ review comment ที่ตรงไปตรงมา และดันให้ PR อยู่ในสถานะ merge ได้

**เหมาะกับ:** ใช้นอก poteto-mode เมื่อผู้ใช้ต้องการให้ดูแล PR หนึ่งตัวต่อเนื่อง (ใน poteto-mode ให้ใช้ playbook Babysit แทน)

**ขั้นตอน**
1. ดึงสถานะ PR ด้วย `gh pr view`
2. Triage ตามลำดับ: conflict → `fix-merge-conflicts`, CI fail → `fix-ci`, comment → `get-pr-comments` ส่วน comment จาก bot ให้คัดแยกเป็น fix / dismiss / ask
3. วนเช็กด้วย `loop` (CI ใช้ `--watch`, รอ reviewer เช็กทุก 20-30 นาที)
4. หยุดเมื่อเขียวครบ หรือแก้ครบ 3 รอบแล้วยังไม่ผ่าน หรือต้องตัดสินใจเชิงออกแบบ
5. รายงานผล

**ข้อห้าม:** ห้ามเขียนประวัติ branch ที่คนอื่น pull ไปแล้วใหม่, ห้ามแก้ค่าที่ test คาดหวังเพื่อให้ผ่าน, ห้าม `--no-verify` และห้ามปิด check ที่ fail

---

### `fix-ci`
**ทำอะไร:** หา check ที่ fail อ่าน log แล้วแก้ทีละจุดจนเขียว

**เหมาะกับ:** CI ของ branch หรือ PR ที่ fail

**ขั้นตอน:** `gh pr checks` → หา error แรกที่แก้ได้ → แก้ให้น้อยที่สุด → push → เช็กอีกครั้ง → วนจนเขียว
**กฎ:** แก้ทีละ failure และใช้ `gh pr checks` เป็นแหล่งความจริง

---

### `fix-merge-conflicts`
**ทำอะไร:** แก้ merge conflict แบบไม่ต้องโต้ตอบ แล้วตรวจ build และ test

**ขั้นตอน**
1. หาไฟล์ที่ conflict
2. แก้แบบให้ความถูกต้องมาก่อน

4. สร้าง lockfile ใหม่ด้วย package manager
5. compile, lint และรัน test
6. stage แล้วสรุป

**ข้อห้าม:** ห้ามมี conflict marker เหลืออยู่, ห้าม refactor ระหว่างแก้ และห้าม push

### K.1 Core: วิธีคิดพื้นฐาน

#### `principle-laziness-protocol`
**ใช้เมื่อ:** refactor, ประเมินขนาด diff หรืออยากเพิ่ม abstraction, layer หรือการส่ง signal ผ่านหลายชั้น
**แนวคิด:** ได้ผลมากที่สุดด้วยโค้ดและความซับซ้อนน้อยที่สุด
**วิธีปฏิบัติ**
- **เลือกลบก่อน** เมื่อถูกขอให้ปรับปรุง ให้มองหาสิ่งที่ลบได้ก่อนสิ่งที่ต้องเพิ่ม
- **รักษา call hierarchy ให้แบน** ถ้าต้องไล่เกิน 3 ไฟล์หรือ 3 ชั้นเพื่อตอบคำถามหนึ่งข้อ ให้ทำให้แบนลง (interface ที่ทำงานเยอะอยู่ข้างในไม่นับเป็น call chain ลึก)
- **รวมการตัดสินใจไว้ที่เดียว** อย่าตัดสินเรื่องเดียวกันซ้ำหลายที่ ให้มีแหล่งความจริงเดียว แล้วส่งผลต่อเป็น flag ง่าย ๆ
- **ทำ diff ให้เล็ก** โค้ดน้อยบรรทัดดีกว่า boilerplate ที่ดู "สวย"
- **สงสัยการส่ง signal ผ่านหลายชั้น** ถ้างานต้องส่งค่าใหม่ผ่าน type, schema หรือ pipeline หลายชั้น ให้หยุดแล้วหาทางที่ตรงกว่า
- **อุดรอยรั่วเล็ก ๆ** เช่น pass-through เล็ก ๆ, การรั่วของ representation และการตัดสินใจที่ซ้ำ ก่อนที่มันจะลาม

**บททดสอบ:** ถ้านักพัฒนาที่เป็นคนจะรู้สึกเหนื่อยที่ต้องดูแลโค้ดนี้ แปลว่าเป็นทางแก้ที่แย่

#### `principle-foundational-thinking`
**ใช้เมื่อ:** ก่อนเขียน logic ตอนเลือก type และ data structure หลัก ตอนจัดลำดับระหว่าง scaffold กับ feature หรือตอนคิดว่า actor หลายตัวใช้อะไรร่วมกัน
**แนวคิด:** การตัดสินใจเชิงโครงสร้างช่วยรักษาทางเลือกในอนาคต ส่วนการตัดสินใจระดับโค้ดช่วยรักษาความเรียบง่าย
**วิธีปฏิบัติ**
- **Data structure มาก่อน** กำหนด type หลักตั้งแต่ต้น ไล่ทุกรูปแบบการเข้าถึงข้อมูล แล้วเลือกโครงสร้างที่เหมาะกับเส้นทางหลัก
- **DRY ที่โครงสร้าง ไม่ใช่ทุกบรรทัด** มีคำสั่งคล้ายกันสามบรรทัดยังดีกว่า abstraction ที่ทำเร็วเกินไป และเขียนให้ชัดดีกว่าเขียนให้ฉลาด
- **ข้อพ่วงเรื่อง concurrency** ก่อนให้หลาย actor ใช้ state ร่วมกัน ให้ถามว่า "ถ้ามีคนอื่นแก้พร้อมกันจะเกิดอะไร" ถ้าคำตอบไม่ใช่ "ไม่มีอะไร" ให้แยกออกจากกัน
- **Scaffold ก่อน** อะไรที่ทุก phase หลังจากนี้ได้ประโยชน์ เช่น CI, lint, test infrastructure และ shared types ให้ทำก่อน ตั้งค่าก่อนทำ feature และเขียน test ก่อนแก้
- แต่ละรอบต้องเพิ่ม abstraction ที่สมบูรณ์ในตัว หรือทำให้ abstraction เดิมลึกขึ้น ไม่ใช่กระจายความสามารถใหม่ไปเป็นเงื่อนไขพิเศษตามจุดที่เรียกใช้
- ลบโค้ดที่ไม่ใช้ก่อน แล้วค่อยวางฐาน

#### `principle-redesign-from-first-principles`
**ใช้เมื่อ:** ต้องเพิ่ม requirement ใหม่เข้าไปใน design ที่มีอยู่
**แนวคิด:** ไม่แปะของใหม่ทับของเดิม ให้ออกแบบใหม่เหมือนว่า requirement นั้นมีมาตั้งแต่ต้น
**วิธีปฏิบัติ**
1. อ่านทุกไฟล์ที่ได้รับผลกระทบจนเข้าใจ design ปัจจุบัน
2. ถามว่า "ถ้าเขียนใหม่ตั้งแต่ศูนย์โดยมี requirement นี้ตั้งแต่แรก จะสร้างอะไร"
3. ไล่แก้ทุกจุดที่อ้างถึง ได้แก่ type, docs, ตัวอย่าง และ rationale
4. คิด redesign ให้จบทั้งก้อน แต่ส่งมอบทีละส่วน

**ต่างจาก `attack-the-premise`:** ข้อนี้สร้าง design ใหม่รอบ requirement ใหม่ ส่วน attack-the-premise ตั้งคำถามกับสมมติฐานเกี่ยวกับระบบที่มีอยู่

#### `principle-attack-the-premise`
**ใช้เมื่อ:** แก้ไปแล้วตั้งแต่ 2 ครั้งขึ้นไป ทุกครั้งตั้งอยู่บนสมมติฐานเดียวกัน และยัง fail ที่ gate เดียวกัน
**แนวคิด:** ปัญหาอาจไม่ได้อยู่ที่วิธีแก้ แต่อยู่ที่สมมติฐานที่ทุกวิธีใช้ร่วมกัน
**วิธีปฏิบัติ**
1. เขียนสมมติฐานที่การแก้ทุกครั้งใช้ร่วมกันออกมาให้ชัด
2. ก่อนลองแก้ครั้งถัดไป ให้หาการสังเกตหรือการทดลองที่หักล้างสมมติฐานนั้นได้
3. ออกแบบการทดลองให้ตรงกับสมมติฐาน เช่น ถ้าเพิ่ม timeout ไปสองครั้งแล้ว อาจกำลังสมมติว่า request ไปถึงปลายทางที่ถูกต้อง ให้ตรวจปลายทางจริงก่อนเพิ่ม timeout อีก
4. ถ้าสมมติฐานเกี่ยวกับการแบ่งงานไม่เท่ากัน ให้นับงานหรือทรัพยากรต่อ actor แล้วไล่การมอบหมาย แนะนำให้กระจายใหม่ได้ก็ต่อเมื่อมีหลักฐานเชื่อมโยงกับความล้มเหลว การกระจายที่เท่ากันทำให้สมมติฐานเรื่องความไม่สมดุลอ่อนลง แต่ไม่ได้ตัดความเป็นไปได้ว่ามี defect ร่วมกัน
5. ถ้ามีประโยชน์ ให้เก็บการทดลองไว้รันซ้ำได้ (build-the-lever) แต่ไม่ต้องทำแบบนี้กับทุกบั๊ก

#### `principle-subtract-before-you-add`
**ใช้เมื่อ:** จัดลำดับงานเพิ่ม feature, refactor หรือ rewrite
**แนวคิด:** การเพิ่มของเข้าไปในระบบที่ซับซ้อนทำให้ความซับซ้อนทบต้น การลบก่อนทำให้เหลือโค้ดน้อยลง เห็นโครงสร้างที่จำเป็น และมักทำให้ design ถัดไปชัดขึ้นเอง
**วิธีปฏิบัติ**
- ลบก่อนสร้าง
- ตัดให้เหลือขั้นต่ำก่อน แล้วค่อยขัดเกลาคุณภาพ
- ออกแบบตามการใช้งานที่เห็นจริง ไม่ใช่ edge case ที่คาดเดา
- ไม่ใส่ validator, parser หรือ guard เกินกว่าที่ spec ต้องการ
- ทำ prompt ให้เรียบง่าย ตัดคำสั่งที่ซ้ำและ template ที่มากเกินไป
- reference ที่ไม่มีเนื้อหาใหม่ให้ลบทิ้ง อย่าทิ้งไว้เป็น stub
- ทุกครั้งที่ออกจากงาน ให้ระบบเรียบง่ายขึ้นเล็กน้อย โดยทำได้มากขึ้นผ่าน surface ที่เท่าเดิมหรือเล็กลง

#### `principle-minimize-reader-load`
**ใช้เมื่อ:** รีวิวหรือปรับโค้ดที่ไล่ตามยาก
**แนวคิด:** maintainability คือปริมาณงานที่คนอ่านต้องใช้เพื่อเข้าใจโค้ด วัดจาก 2 แกนที่ไม่ขึ้นต่อกัน
1. **จำนวนชั้นที่ต้องไล่** ระหว่างคำถามกับคำตอบ
2. **ปริมาณ state ที่ต้องจำไว้ในหัว** ทั้งแบบซ่อนอยู่และแบบเปลี่ยนค่าได้

ไฟล์แบนที่มี global 50 ตัวอาจอ่านยากพอ ๆ กับ adapter ซ้อน 6 ชั้น ส่วน LOC และ cyclomatic complexity เป็นแค่ตัวแทน
**วิธีปฏิบัติ**
- **ยุบชั้นที่ไม่คุ้ม** เช่น wrapper ที่มีผู้เรียกคนเดียว, adapter ที่ไม่มี implementation ที่สอง หรือ indirection ที่เผื่อไว้แต่ไม่เคยได้ใช้
- **ชั้นที่ติดกันต้องเปลี่ยนระดับ abstraction** ชั้นที่แค่ส่ง method และ argument เดิมต่อไปให้ยุบทิ้ง
- **interface ต้องซ่อนความซับซ้อนได้จริง** interface กว้างที่ซ่อนอะไรได้น้อย บังคับให้คนอ่านต้องเรียนทั้ง surface และ implementation
- **ลดขอบเขตของ state** เรียงจากดีไปแย่: pure function → ตัวแปร local → field → module state → global และใช้การคำนวณจากค่าที่มีแทนการ sync ค่าซ้ำ
- **ระบุ invariant ไว้ที่ขอบเขต** ไม่ใช่ซ้ำในทุกจุดที่ใช้
- ก่อนเพิ่มชั้นหรือ state ให้ถามว่ามันลดภาระของคนอ่านที่อื่นได้มากเท่ากับที่เพิ่มหรือไม่

**บททดสอบ:** คนอ่านใหม่ตอบได้ภายใน 30 วินาทีไหมว่า "X มาจากไหน" และ "อะไรเปลี่ยน X ได้บ้าง"

#### `principle-outcome-oriented-execution`
**ใช้เมื่อ:** rewrite หรือ migration ที่วางแผนไว้และมีขอบเขตของแต่ละ phase ชัดเจน
**แนวคิด:** ให้ความสำคัญกับสถานะปลายทางที่ตรวจได้ มากกว่าการทำให้ทุกขั้นกลางทางเสถียร เพราะ compatibility code ชั่วคราวมักอยู่นานจนกลายเป็นหนี้
**กฎ**
- ความสมบูรณ์ของปลายทางสำคัญกว่าความเสถียรระหว่างทาง
- ยอมให้พังระหว่างทางได้ ถ้าวางแผนไว้ มีขอบเขต และย้อนกลับได้

**ข้อควบคุม**
- ใช้กับ rewrite หรือ migration ที่มีขอบเขต phase ชัดเจนเท่านั้น
- ประกาศให้ชัดว่ายอมให้พังได้ตรงไหน
- ยังคงรัน check สำคัญในส่วนที่กำลังแก้อยู่
- เมื่อจบแผน ต้อง verify ครบทั้ง static และ runtime

#### `principle-experience-first`
**ใช้เมื่อ:** ต้องเลือกระหว่างเรื่องผลิตภัณฑ์, UX หรือขอบเขตของ feature
**แนวคิด:** ถ้าความสะดวกในการ implement ขัดกับความพอใจของผู้ใช้ ให้เลือกความพอใจของผู้ใช้
**วิธีปฏิบัติ**
- ทุก feature, control และ option ต้องมีเหตุผลรองรับ
- ทำน้อยแต่ดี เช่น 3 feature ที่เนี้ยบดีกว่า 10 feature ที่หยาบ
- ทำ prototype ก่อนตัดสินใจ เพราะการตัดสินใจเชิงออกแบบใน HTML ที่ใช้แล้วทิ้งถูกกว่าในโค้ด production
- ใส่ใจรายละเอียด เช่น transition, alignment, spacing, feedback และ error state
- ทำให้ core loop กระชับ feature ไหนไม่ช่วย workflow หลักก็ไม่ควรขวางทาง

**ใครคือ "ผู้ใช้":** คนที่ใช้ผลงาน ถ้าเป็น UI คือผู้ใช้ปลายทาง ถ้าเป็น library หรือ internal API คือเพื่อนร่วมงานที่ import ไปใช้ และวิศวกรที่จะดูแลโค้ดต่อก็นับเป็นผู้ใช้ด้วย
**ความสัมพันธ์กับข้ออื่น:** `foundational-thinking` กำหนด **ลำดับ** ของงาน ส่วนข้อนี้กำหนด **เป้าหมาย**

#### `principle-exhaust-the-design-space`
**ใช้เมื่อ:** มี interaction ใหม่หรือการตัดสินใจเชิงสถาปัตยกรรมที่ไม่มีแบบให้ดูใน codebase
**แนวคิด:** สร้างของผิดแพงกว่าการสำรวจ 3 ทางเลือก
**กฎ:** ถ้าคำตอบที่ถูกไม่ชัด ให้ทำ prototype หรือ sketch 2-3 แบบ แล้ววางเทียบกันก่อนตัดสินใจ (หรือที่เรียกว่า "design it twice") แบบที่สองที่เป็นแค่รูปแบบย่อยของแบบแรกไม่นับ
**ใช้เมื่อ:** UI interaction ที่ไม่เคยมีใน codebase, ทางเลือกเชิงสถาปัตยกรรมที่เป็นไปได้หลายแบบ หรือการตัดสินใจเชิงผลิตภัณฑ์ที่ขึ้นกับความรู้สึกในการใช้งาน
**ไม่ใช้เมื่อ:** งานเชิงกลไกที่มีแบบอยู่แล้ว, บั๊กหรือ refactor ที่เป้าหมายชัด หรือเมื่อข้อจำกัดเหลือทางเดียว
**ใช้จริงใน:** `architect` (ต้องมีอย่างน้อย 2 แบบ) และ playbook Prototype (ใช้ switcher)

#### `principle-build-the-lever`
**ใช้เมื่อ:** งานที่ไม่ง่ายทุกชนิด ไม่เฉพาะงานซ้ำ ๆ เช่น การแก้โค้ด, migration, การวิเคราะห์ และการตรวจสอบ
**แนวคิด:** สร้างเครื่องมือที่ทำงานหรือพิสูจน์งาน แทนการทำมือ ได้ประโยชน์ 2 ทาง
- **Throughput:** codemod หรือ script ทำงานเหมือนเดิมทุกครั้งและรันซ้ำได้ฟรี
- **Confidence:** reviewer อ่านและรันเครื่องมือซ้ำได้ เปลี่ยน "เชื่อผมเถอะ" เป็น "รันอันนี้ดู"

**วิธีปฏิบัติ**
1. ทำหน่วยแรกด้วยมือเพื่อเรียนรู้สูตร แล้วค่อยสร้างเครื่องมือ จากนั้นรันเครื่องมือกับหน่วยแรกแล้ว diff เทียบกับที่ทำมือ
2. เลือกเครื่องมือให้เหมาะกับงาน: codemod หรือ script สำหรับแก้โค้ด, generator สำหรับไฟล์ซ้ำ ๆ, dump ลง sqlite สำหรับวิเคราะห์ และ check ที่รันซ้ำได้สำหรับ verify
3. **เครื่องมือที่ให้ผลแน่นอนดีกว่าการ fan-out** ถ้า script ทำครบในรอบเดียวได้ ให้รันเอง ไม่ต้องส่ง subagent ไปทำมือ
4. ถ้าต้องกระจายงานให้ subagent ให้เขียนเครื่องมือเป็น skill ที่ทุกตัวอ่าน มีทั้งสูตร, contract ของการ verify และสิ่งที่ห้ามแตะ และเก็บไว้นอกพื้นที่ที่ subagent เขียนได้
5. commit เครื่องมือไว้ถ้างานยาวกว่า session

**สัญญาณเตือน:** ถ้าอ้าง principle นี้แต่ไม่มี codemod, script, generator หรือ skill อยู่ใน diff แปลว่าไม่ได้ใช้จริง
**ความสมดุล:** เกณฑ์คือความง่ายของงาน ไม่ใช่ความซ้ำ งานครั้งเดียวก็ควรมีเครื่องมือถ้าเครื่องมือทำให้ตรวจงานได้ และให้สร้าง script ที่เล็กที่สุด ไม่ใช่ framework
**ต่างจาก `encode-lessons-in-structure`:** ข้อนั้นเปลี่ยนคำสั่งที่ซ้ำเป็นกลไกถาวร ส่วนข้อนี้เน้น throughput และการตรวจงานที่อยู่ตรงหน้า

### K.2 Architecture: การออกแบบโค้ด

#### `principle-model-the-domain`
**ใช้เมื่อ:** เขียน logic ที่มี state, โค้ดที่มี branch เยอะ หรือมีการสมมติรูปร่างข้อมูลแบบเดียวกันซ้ำหลายไฟล์
**แนวคิด:** เก็บ domain ไว้ในโครงสร้างข้อมูล แทนการกระจายไปใน if ต่าง ๆ โครงสร้างที่ตรงกับ domain ทำให้ state ที่ผิดเกิดขึ้นไม่ได้และลด branch การเลือกโครงสร้างตอนเขียนมีต้นทุนต่ำ แต่ถ้าปล่อยไว้แก้ทีหลัง มักกลายเป็นงาน refactor ที่ถูกเลื่อนออกไปเรื่อย ๆ
**โครงสร้างที่ควรใช้**
| แทนที่ | ด้วย |
|---|---|
| boolean, phase หรือ lifecycle check ที่กระจาย | state machine |
| parameter หลวม ๆ หรือการสมมติรูปร่างข้อมูลซ้ำ | typed object/model |
| branching ที่กระจายข้ามไฟล์ | map, registry, lookup table หรือ discriminated union |
| การแก้ state แบบเฉพาะกิจ | reducer หรือ command/event model |
| module ที่แบ่งตามลำดับขั้น (load → validate → transform → save) | module ที่แบ่งตามความรู้ของ domain |
| พฤติกรรมหรือ invariant ที่ซ้ำ | module boundary เล็ก ๆ |
| การเข้าถึงข้อมูลแบบเฉพาะ | queue, cache, index, graph/tree หรือ normalized collection |

**ข้อควรระวัง:** อย่าฝืนสร้าง abstraction ถ้าโค้ดปัจจุบันชัด อยู่ในที่เดียว และไม่น่าจะโต ให้ใช้โค้ดธรรมดา และระวัง abstraction ที่เพิ่ม indirection แต่ไม่ได้ลด branch, กฎที่ซ้ำ หรือ state ที่ผิด
**สัญญาณเตือน:** feature ใหม่ทำให้ if/else เดิมยาวขึ้นอีกหนึ่ง branch, มี boolean ตัวที่สองที่ต้อง sync กับตัวแรก หรือมี module ที่ตั้งชื่อตาม phase แล้วกฎ domain เดียวกันซ้ำอยู่หลายขั้น

#### `principle-boundary-discipline`
**ใช้เมื่อ:** เขียน validation, error handling หรือ framework adapter
**แนวคิด:** วาง validation, type narrowing และ error handling ไว้ที่ขอบระบบ ข้างในให้เชื่อ type ได้เลย business logic อยู่ใน pure function และชั้นนอกบางและเป็นเชิงกลไก
**วิธีปฏิบัติ**
- **ที่ขอบระบบ** (CLI args, config, external API, network): validate, คืน error และป้องกันเต็มที่
- **ภายในระบบ:** ใช้ข้อมูลที่มี type, ส่ง error ต่อ และไม่ validate ซ้ำ
- **ข้ามขอบระบบ:** เปิดเผยแนวคิดของ domain ไม่ใช่ representation ภายในของขอบระบบ กลไกทั่วไปอยู่ข้างใน นโยบายเฉพาะอยู่ที่ขอบ
- validate config ตอน parse ไม่ใช่ใน business logic
- ไม่ re-export type ของ transport, storage, framework หรือ wire ผ่าน public surface
- ไม่ใส่ nil check ซ้ำซ้อนลึก ๆ ใน call chain ถ้าขอบระบบตรวจแล้ว
- ทำ parse function, prompt construction และ scoring ให้เป็น pure transform

**บททดสอบ:** "ข้อมูลนี้กำลังข้ามขอบระบบอยู่ไหม" ถ้าไม่ การ validate นั้นซ้ำซ้อน และ "ส่วนนี้เป็น pure function ที่ชั้นนอกแค่เรียกใช้ได้ไหม" ถ้าได้ ให้แยกออกมา

#### `principle-type-system-discipline`
**ใช้เมื่อ:** ออกแบบ type, รีวิว signature หรือเขียนภาษาที่มี static type
**แนวคิด:** ใช้ type checker เหมือนเครื่องพิสูจน์ กำจัด state ที่เป็นไปไม่ได้, primitive ที่ใช้สลับกัน และ variant ที่ไม่ได้จัดการ ตั้งแต่ตอน compile
**วิธีปฏิบัติ**
- **ทำให้ state ที่ผิดเขียนออกมาไม่ได้** ใช้ sum type (discriminated union, enum ที่มี payload, sealed class) แทน object ที่เต็มไปด้วย optional field ตัวอย่างที่ผิดคือ `{ completed: boolean; completedAt?: Date }` ซึ่งยอมให้มี `completed: true` แต่ไม่มี `completedAt`
- **สร้าง type จากค่าที่ต้องการ แทนการตัดออกจาก type ที่กว้างกว่า** เช่น list ที่ไม่ว่างคือ head + rest และช่วงเวลาที่ถูกต้องคือ start + duration
- **ติด brand ให้ primitive** `UserId` กับ `OrderId` ไม่ควรใช้สลับกันได้ validate ครั้งเดียวตอนสร้าง แล้วเชื่อ type ต่อจากนั้น
- **ข้อมูลภายนอกไม่มี type จนกว่าจะ parse** ได้แก่ JSON, RPC, CLI args, env และแถวจาก DB
- **อย่าโกหก type system** cast และ assertion ที่เลี่ยง compiler คือ crash ที่รอเกิดตอน runtime
- **ให้ compiler ตรวจว่าครอบคลุมทุกกรณี** เช่น `never` ใน TypeScript หรือ `match` ใน Rust
- **สร้าง type จาก schema ที่เป็นแหล่งความจริง** เช่น protobuf, OpenAPI, GraphQL หรือ migration
- **เพิ่มความแข็งของ type เฉพาะจุดที่ฟังก์ชันไม่ครอบคลุมทุก input** null check หรือ throw แบบ "ไม่ควรเกิด" คือสัญญาณว่า type อ่อนเกินไป ให้ย้ายการตรวจนั้นขึ้นไปเป็น type แล้วหยุด

**บททดสอบ**
- เขียน comment อธิบายได้ไหมว่าการผสม field แบบไหนถูกต้อง ถ้าได้ แปลว่า type หลวมเกินไป ให้แยกเป็น sum type
- มี argument สองตัวที่เป็น primitive เดียวกันแต่ความหมายต่างกันไหม ถ้ามี ให้ติด brand
- `any`, `as` หรือ `assertNotNull` ตัวนี้มาจากไหน ให้ไล่กลับไปที่ขอบระบบแล้ว validate ที่นั่น
- ถ้าเดือนหน้ามี variant ใหม่ compiler จะบอก agent คนถัดไปไหมว่าต้องเพิ่ม case ที่ไหน
- type นี้ซ้ำกับรูปร่างที่ไฟล์อื่นเป็นเจ้าของหรือเปล่า ถ้าใช่ ให้ derive แทน

#### `principle-make-operations-idempotent`
**ใช้เมื่อ:** ออกแบบ command, lifecycle step หรือ processing loop ที่ต้องเจอ crash, restart และ retry เป็นเรื่องปกติ
**แนวคิด:** ทุก operation ต้องได้สถานะที่ถูกต้องเหมือนกัน ไม่ว่าจะรันกี่ครั้งหรือเริ่มจากจุดไหน
**วิธีปฏิบัติ**
- **startup ที่ไปถึงสถานะเดียวกันเสมอ:** สแกน state ที่มีอยู่, ล้าง artifact ค้าง และรับ session ที่ยังมีชีวิตมาดูแลต่อ
- **cleanup ตามเนื้อหา:** เทียบจากความเหมือนของเนื้อหา ไม่ใช่ลำดับการสร้าง
- **lock ที่ซ่อมตัวเองได้:** ตรวจ lock ค้างจาก PID
- **การ schedule ที่รันซ้ำได้:** งานที่ fail ถูก spawn ใหม่ได้อย่างสะอาด และ input ถูกสร้างใหม่ทุกรอบ

**บททดสอบ:** ถ้ารันสองครั้งติดกันจะเป็นอย่างไร, ถ้ารอบก่อน crash ตรงจุดไหนก็ได้จะเป็นอย่างไร และรันซ้ำแล้วได้สถานะสุดท้ายเดิมไหม ถ้าคำตอบคือ "ขึ้นกับ state ที่เหลืออยู่" แปลว่าต้องมีขั้น reconcile
**ใช้จริงใน pstack:** `setup-pstack` เขียนไฟล์ทับทั้งไฟล์ และ `orch` แทนที่ lock เมื่อ PID ของเจ้าของ lock ไม่อยู่แล้ว

#### `principle-migrate-callers-then-delete-legacy-apis`
**ใช้เมื่อ:** เพิ่ม API ภายในตัวใหม่ ในขณะที่ผู้เรียกตัวเดิมยังมีอยู่
**แนวคิด:** เมื่อตัดสินแล้วว่า API ใหม่คือ design ที่ถูก ให้ย้ายผู้เรียกและลบ API เก่าในรอบเดียวกัน ถ้าเก็บทั้งสองไว้ จะมีสองเส้นทางที่ต้องดูแล การ cleanup จะช้าลง และ codebase จะมีแต่ของที่ถูกเพิ่มเข้ามา ไม่เคยถูกลบออก
**วิธีปฏิบัติ**
- ไม่เก็บ API เก่าไว้เพียงเพราะยังมีผู้เรียกภายใน
- ทำรายการผู้เรียก ย้ายทั้งหมด แล้วลบทันที
- adapter ชั่วคราวเป็นข้อยกเว้นที่ต้องมีกำหนดเวลา ไม่ใช่สถาปัตยกรรมปกติ
- แก้ test ให้ตรวจ contract ใหม่ และลบ test ที่ปกป้องแค่รายละเอียดของ implementation เก่า

**เงื่อนไข:** ไม่มีผู้ใช้ภายนอกที่ต้องพึ่ง backward compatibility, โปรเจกต์รับ breaking change ที่ประสานกันได้ และ API ใหม่เป็นส่วนหนึ่งของการทำให้ระบบเรียบง่ายลง

#### `principle-separate-before-serializing-shared-state`
**ใช้เมื่อ:** actor หลายตัวอาจเขียนไฟล์, branch, key หรือ state object เดียวกันพร้อมกัน
**แนวคิด:** ถามก่อนว่าจำเป็นต้องใช้ object เดียวกันจริงไหม ถ้าไม่ ให้กำจัดการใช้ร่วมกัน ถ้าจำเป็นจริง ให้บังคับลำดับด้วยโครงสร้าง **คำสั่งหรือข้อตกลงไม่ใช่ concurrency control**
**วิธีปฏิบัติ**
1. ระบุ state ที่ใช้ร่วมกันและเปลี่ยนค่าได้ เช่น ไฟล์ที่ทั้งอ่านและเขียน, branch ที่ push ร่วมกัน หรือ API ที่ทั้งนิยามและใช้
2. **ค่าเริ่มต้นคือกำจัดเป้าหมายที่เขียนร่วมกัน** ให้แต่ละ actor มีไฟล์, key, branch หรือ directory ของตัวเอง แล้วค่อยรวมตอนอ่านหรือรายงาน ตัวอย่างเช่น worker สองตัวเขียน field ของตัวเองลง `state.json` ไฟล์เดียวก็ยังนับเป็นการเขียนร่วม ส่วน `indexer-state.json` กับ `metrics-state.json` ไม่นับ
3. ใช้การจัดลำดับเชิงโครงสร้างเฉพาะเมื่อการมีเป้าหมายเดียวเป็น invariant จริง เช่น lockfile, phase ที่ทำต่อกัน, actor ที่เขียนได้ตัวเดียว หรือ atomic compare-and-swap และให้มองความคิด "ต้องมี lock" เป็นสัญญาณให้ตรวจ design ก่อน

**ใช้จริงใน pstack:** worktree แยกต่อ writer ทุกตัว, ไฟล์ใน store ของ Orchestrate มี writer คนเดียว และ output path แยกต่อ candidate ใน `arena`

### K.3 Verification: การพิสูจน์ผล

#### `principle-prove-it-works`
**ใช้เมื่อ:** ทำงานเสร็จแล้ว ก่อนประกาศว่าเสร็จ
**แนวคิด:** ตรวจของจริงโดยตรง ไม่อนุมานจากตัวแทน, รายงานที่ทำเอง หรือ "compile ผ่าน" ถ้าทำตามข้อสรุปที่ผิดจะเสียมากกว่าการตรวจแหล่งจริง
**วิธีปฏิบัติ**
- ตรวจว่า process ยังมีชีวิตโดยตรง ไม่ดูผ่าน state ที่คำนวณต่อมา
- อ่านค่าจริง ไม่ใช่ค่าที่ cache หรือค่าที่คำนวณต่อมา
- ถ้าการตรวจ fail ให้สงสัยวิธีสังเกตก่อนสงสัยระบบ
- **ตรวจกระบวนการด้วย ไม่ใช่แค่ผลลัพธ์** ผลที่ถูกอาจมาจากกระบวนการที่พัง เช่น ข้อกำหนดที่บังเอิญถูกจากไฟล์ที่ไม่เคยอ่าน ทุกข้อเท็จจริงที่ใช้ต้องบอกได้ว่ามาจากบันทึกไหน
- **สีแดงไม่ใช่การวัดผล** test ที่ fail พิสูจน์ได้ก็ต่อเมื่อเนื้อหาของความผิดพลาดตรงกับที่คาดไว้ เพราะ exception, collection ว่าง และ mismatch จริงแสดงเป็นสีแดงเหมือนกันหมด ให้ยก diff ของ assertion มาแสดง ไม่ใช่ตัว assertion
- **เขียนการตรวจเป็น script ถ้าทำได้** script ที่รันซ้ำได้เป็นหลักฐานที่แข็งที่สุด เก็บ output ไว้ให้ reviewer รันซ้ำ และ commit เฉพาะงานใหญ่ที่ต้องตรวจย้อนหลังได้

#### `principle-fix-root-causes`
**ใช้เมื่อ:** debug
**แนวคิด:** การแก้ที่อาการจะสะสมจนระบบเข้าใจยากขึ้น และบั๊กจริงยังอยู่ การแก้ที่ต้นเหตุช้ากว่าในตอนแรก แต่ลดเวลา debug รวม
**วิธีปฏิบัติ**
- reproduce ก่อน
- ถาม "ทำไม" ไปเรื่อย ๆ จนถึงต้นเหตุ
- ไม่ใส่ guard เพื่อปิดอาการ (การเพิ่ม nil check เพื่อให้ไม่ crash คือการแก้ที่อาการ)
- ถ้า workaround ต้องมี comment ยาวเป็นย่อหน้าเพื่ออธิบาย แปลว่าโค้ดผิด ให้แก้โค้ด ไม่ใช่แก้ comment
- หาแบบแผน ไม่ใช่แค่จุดเดียว (grep หาจุดอื่นที่มีปัญหาเดียวกันแล้วแก้ทั้งหมด)
- ถ้าติด ให้ใส่ instrumentation อย่าเดา

**บั๊กที่เกิดหลัง restart:** ให้สงสัย state ที่ค้างอยู่ก่อนโค้ด เช่น config, cache, lock file หรือ state ที่ serialize ไว้ ถ้าลบไฟล์ state แล้วกลับมาทำงานได้ ให้แก้ที่การตรวจ state

#### `principle-sequence-verifiable-units`
**ใช้เมื่อ:** งานหลายขั้น เช่น sweep, migration หรือการแก้แบบเดียวกันหลายที่ รวมถึงการเรียง commit และ PR
**แนวคิด:** ถ้าเจอปัญหาที่หน่วยที่ทำให้เกิด จะหาจุดได้ง่าย แต่ถ้าเจอหลังทำไปเป็นชุด ปัญหาจะจมอยู่ใต้งานที่สร้างทับไปแล้ว
**วิธีปฏิบัติ**
- **ตอนทำงาน:** ทุกหน่วยมีกรอบ before/after คือเริ่มจากสถานะที่รู้ว่าดี → เปลี่ยนหนึ่งอย่าง → รัน check → ไปต่อ และ rebase บน trunk ที่สะอาดก่อน เพื่อให้ check วัดเทียบกับ baseline จริง
- **ตอนส่งมอบ:** เรียง commit และ PR ให้ลำดับพิสูจน์งานเอง แบบมาตรฐานคือ failing test ก่อน แล้ว fix ทับ แบบอื่น ๆ เช่น ลบก่อนปรับรูป, เก็บ baseline ก่อนทำ treatment หรือ scaffold ก่อน feature

**ความสัมพันธ์:** `prove-it-works` ทำให้แต่ละ check เป็นของจริง ส่วน `build-the-lever` ทำให้ check ต่อหน่วยมีต้นทุนต่ำ

#### `principle-test-behavior-not-implementation`
**ใช้เมื่อ:** เขียน แก้ หรือตัดสินใจว่าจะเก็บ test ไว้หรือไม่
**แนวคิด:** ก่อนเก็บ test ให้นึกถึงบั๊กที่เกี่ยวข้องหนึ่งตัว แล้วดูว่า test ทั้งชุดจับบั๊กนั้นได้จริงไหม ถ้าทำได้ ให้ลองใส่บั๊กนั้นชั่วคราวแล้วดูว่า test fail
**วิธีปฏิบัติ**
- `toBeDefined` จับได้แค่กรณีไม่มีผลลัพธ์ แต่ยอมรับผลที่ผิด ถ้า contract ต้องการค่าเฉพาะ ให้ตรวจค่านั้น
- **เก็บ assertion ที่ตรวจว่าไม่มีบางอย่างเกิดขึ้น** ถ้า contract กำหนดไว้ เช่น operation ที่ถูกปฏิเสธต้องไม่ส่ง email ให้ตรวจว่า outbox ว่าง
- เก็บการตรวจค่าคงที่เฉพาะค่าที่เป็น contract กับผู้ใช้ อย่าตรึงค่าคงที่ที่บังเอิญเป็นแบบนั้นหรือถ้อยคำใน prompt
- ระวังค่าที่คาดหวังซึ่งคำนวณผ่าน path เดียวกับที่ผิด เพราะจะยืนยันตัวเอง ให้ใช้ค่าคาดหวังที่ได้มาอย่างอิสระ
- ดู setup กับ body ของ test ไปพร้อมกัน การ assert แค่ fixture ที่ไม่ได้ถูกแตะไม่นับ

**ปฏิเสธ test ที่:** ไม่ได้เรียกอะไรที่เกี่ยวข้อง, ไม่ assert อะไรที่มีความหมาย หรือแค่ตรวจว่า mock ถูกเรียก โดยไม่ตรวจผลจริง

#### `principle-explain-the-number`
**ใช้เมื่อ:** ก่อนเชื่อ รายงาน หรือตัดสินใจจากตัวเลขที่วัดได้ เช่น speedup, regression, throughput, latency หรือผล eval
**แนวคิด:** ตัวเลขที่วัดได้คือข้อกล่าวอ้างเกี่ยวกับระบบ การรันที่ผิดพลาดก็ยังพิมพ์ตัวเลขที่ดูน่าเชื่อได้ ถ้าบอกไม่ได้ว่าทำไมไม่ดีกว่านี้สองเท่า แปลว่ายังไม่รู้ว่าวัดอะไรอยู่
**วิธีปฏิบัติ**
- **ถาม "ทำไมไม่ได้สองเท่า"** ระบุทรัพยากรที่จำกัดผล เช่น core, lock, disk, network หรือตัวสร้าง load เอง ให้หาจาก profile หรือ counter ของระบบ ไม่ใช่เดาจากการอ่านโค้ด
- **ไล่ว่าตัวเลขอาจวัดอะไรอื่นอยู่** แล้วตัดทีละข้อด้วยหลักฐาน ตัวที่ต้องสงสัยบ่อยคือ error, งานที่ถูกข้ามหรือ cache, ฝั่งที่ไม่ได้ tune, noise และส่วนที่เล็กเกินจะมีผลแบบ end-to-end
- **เก็บหลักฐานไว้คู่ตัวเลข** ได้แก่ จำนวนรอบ, spread และตัวจำกัด

**สัญญาณเตือน:** ไม่มีจำนวนรอบ ไม่มี spread หรือไม่มีตัวจำกัด หรือเวลาที่ประหยัดได้มากกว่าเวลาที่ส่วนที่แก้ใช้อยู่เดิม
**ใช้คู่กับ:** skill `benchmark-checklist` สำหรับตัวเลข performance ส่วนผล eval ให้ถามว่าทุกรอบทำงานจริงไหม และผลต่างคงอยู่ข้ามรอบและข้ามโมเดลไหม

### K.4 Delegation: การมอบงาน

#### `principle-guard-the-context-window`
**ใช้เมื่อ:** context ใกล้เต็ม เช่น output ใหญ่, ไฟล์ยาว, อ่านซ้ำ หรือวางแผน fan-out
**แนวคิด:** context window มีจำกัดและเติมคืนไม่ได้ภายใน session ถ้าล้นจะทำให้การคิดแย่ลง
**วิธีปฏิบัติ**
- **แยกข้อมูลก้อนใหญ่ออกไป** output ยาว, screenshot และเอกสารใหญ่ให้ subagent จัดการ แชตหลักเก็บแค่สรุป
- **เก็บสิ่งที่ใช้บ่อยไว้ในไฟล์ skill** template ที่ใช้ทุกครั้งไม่ควรแยกไฟล์ เพราะต้องเสียค่าอ่านทุกครั้ง
- **กำหนดขนาด phase และจำกัดขอบเขต** จำกัดจำนวนไฟล์ต่อ phase และตั้งงบจำนวน turn

**ความสัมพันธ์:** `minimize-reader-load` คือหลักเดียวกันในฝั่งคน เพราะความจำของคนอ่านก็มีจำกัดเช่นกัน

#### `principle-never-block-on-the-human`
**ใช้เมื่อ:** อยากถามว่า "ทำ X ดีไหม" ในงานที่ย้อนกลับได้
**แนวคิด:** มนุษย์ดูแลงานแบบไม่ต้องอยู่ด้วยตลอด agent ต้องทำงานต่อได้ ทุกการหยุดรออนุญาตทำให้งานติด และทำให้มนุษย์เป็นคอขวด โค้ดย้อนกลับและรีวิวได้ การตัดสินใจผิดจึงมักเสียน้อยกว่าการหยุดรอ
**วิธีปฏิบัติ**
- **ทำก่อน แล้วค่อยแสดงผล** ไม่ถามว่า "ทำ X ดีไหม" ให้ทำ X แล้วอธิบายเหตุผล
- **ทำให้ระบบซ่อมตัวเองได้** ถ้าเห็นปัญหา ให้บันทึกแล้วแก้ในรอบถัดไป

**ขอบเขต**
- งานที่ย้อนกลับไม่ได้ เช่น force-push, ลบข้อมูล production หรือส่งข้อความออกภายนอก ยังต้องขอยืนยัน
- งานที่ย้อนกลับได้ เช่น เขียนโค้ด, แก้ note หรือแบ่งงาน ให้ทำต่อได้เลย
- **ทิศทางของผลิตภัณฑ์มาจากมนุษย์** แต่การลงมือทำไม่ควรติดรอ

### K.5 Meta

#### `principle-encode-lessons-in-structure`
**ใช้เมื่อ:** รู้ตัวว่ากำลังเขียนคำสั่งเดิมเป็นครั้งที่สอง หรือเห็นการแก้ไขแบบเดิมเกิดซ้ำ
**แนวคิด:** คำสั่งที่เป็นข้อความพลาดได้ง่าย เพราะคนอ่านต้องสังเกต จำ และทำตามเอง ส่วนกลไกเชิงโครงสร้างบังคับได้โดยไม่ต้องอาศัยความร่วมมือ
**วิธีปฏิบัติ**
1. ถามว่าทำเป็น lint, metadata flag, runtime check หรือ script ได้ไหม
2. ถ้าได้ ให้ทำ แล้ว **ลบคำสั่งที่เป็นข้อความทิ้ง**
3. ถ้าไม่ได้ เพราะต้องใช้วิจารณญาณ ให้ทำคำสั่งให้เด่นขึ้น และใส่ตัวอย่างความผิดพลาด

**เลือกกลไกที่แรงที่สุด:** type ที่ทำให้ state ผิด compile ไม่ผ่าน → lint หรือ banned API ที่ทำให้ CI fail → helper กลาง → runtime check เหตุผลคือ agent จะลอกสิ่งที่มีอยู่ในโค้ด กลไกที่อ่อนจึงกลายเป็นแบบที่ถูกลอกต่อ
**วงจร:** เก็บทุกการแก้ไข → ส่งไปชั้นที่ถูก (เรื่องครั้งเดียว → note, เรื่องที่ซ้ำ → skill หรือ lint, ปัญหาเชิงระบบ → principle) → ปิดวงจรด้วยการแก้ทันทีหรือสร้าง todo ที่เป็นรูปธรรม
**รูปแบบที่ผิด:** รับรู้แต่ไม่บันทึก ("จะจำไว้"), บันทึกแต่ไม่ส่งต่อ หรือแก้จุดเดียวโดยปล่อยให้แบบแผนเดิมอยู่ต่อ

### Perf issue
**Ownership:** You own the measurement story. Plan, review, verify the numbers. ทุกการแก้ต้องผูกกับการวัด ห้ามอ่าน source แทนการวัด
**เหมาะกับ:** ความช้าที่วัดได้ ต้องการแก้ครั้งเดียว (ถ้าต้องการปรับต่อเนื่อง ให้ใช้ Hillclimb)

**ขั้นตอน**
1. เก็บ baseline trace ผ่าน driver skill แล้วตรวจ baseline และตัวเลขทุกตัวหลังจากนั้นด้วย `benchmark-checklist`
2. ใช้ `how` ช่วยตั้งสมมติฐาน ห้ามอ้างว่าถึงเพดานแล้วถ้ายังไม่ได้รันจริง ใช้กลยุทธ์ 8 ตระกูลเป็นตัวช่วยตั้งสมมติฐาน ไม่ใช่ checklist และจะลองตระกูลไหนได้ก็ต่อเมื่อ trace แสดงสัญญาณของมัน

| ตระกูล | สัญญาณใน trace | วิธีแก้ |
|---|---|---|
| **Elimination** | งานที่ไม่มีใครใช้ผล, gate ที่ปิดตลอด, sync ที่ซ้ำ | ลบทิ้ง (ต้องใช้ `how` เพราะ profiler ไม่บอกว่าอะไรลบได้) |
| **Divide and conquer** | ต้นทุนโตตามขนาด input | chunk, shard, prune หรือทำขนาน |
| **Caching** | คำนวณหรือ fetch ซ้ำด้วย input เดิม | เก็บผลไว้ใช้ซ้ำ และต้องระบุให้ได้ว่าอะไรทำให้ cache หมดอายุ |
| **Indirection** | hot path ทำงานแพงที่ตัวกลางถูกกว่าทำแทนได้ | index แทน scan, queue ย้ายงานออกจาก thread หลัก |
| **Batching** | operation เล็กจำนวนมาก แต่ละครั้งจ่าย overhead คงที่ | รวมเป็น batch |
| **Redundancy** | ต้องรอ instance ที่ช้าตัวเดียว | ส่ง request ซ้ำแล้วเอาตัวที่เร็วที่สุด (ต้องมีทรัพยากรเหลือ) |
| **Lazy evaluation** | คำนวณผลที่ยังไม่ต้องใช้ | เลื่อนไปทำตอนใช้ครั้งแรก |
| **Scheduling** | งานที่ต้องทำ แต่ไม่ต้องทำตอนผู้ใช้รอ | ย้ายไปทำตอน idle, warmup หรือ precompute และวัดที่ path ที่ผู้ใช้รอ |

3. วางแผนจาก trace ถ้าข้าม boundary ให้ใช้ `architect` ส่งงานให้ subagent ที่ใช้โมเดล perf-issue (ค่าเริ่มต้นคือโมเดลที่เก่งที่สุด) แล้วรีวิว diff เก็บ trace หลังแก้ และตรวจทีละความพยายาม
4. แปลง artifact ไปเทียบกัน (JSON → sqlite, diff) ผล inconclusive ไม่นับว่าผ่าน
5. อ้างตัวเลขที่วัดได้ใน PR
6. Opening a PR

**Reply:** ตัวเลข baseline, ตัวเลขหลังแก้, delta และ path ของ artifact

### Hillclimb
**Ownership:** You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.
**หลักสำคัญ:** เปลี่ยนหนึ่งอย่าง วัดหนึ่งครั้ง แล้วเก็บหรือ revert ห้ามซ้อนการเปลี่ยนที่ยังไม่ได้ทดสอบ และห้ามอ้างว่าได้ผลจากการอ่านโค้ด
**เหมาะกับ:** ปรับ metric เดียวอย่างต่อเนื่องให้ถึงเป้า เช่น เวลา boot, ขนาด bundle หรือ p95 latency

**ขั้นตอน**
1. **เข้าใจ workload ก่อนเลือก metric** ใช้ `how` ระบุมิติที่ทำให้ผลเปลี่ยน (ขนาดข้อมูล, ประวัติ, state, concurrency) แล้วเลือกเคสที่ reproduce ปัญหาที่ผู้ใช้บ่นได้ ถ้า reproduce ไม่ได้ ให้แก้ repro ก่อน จากนั้นกำหนด metric, ทิศทางที่ถือว่าดีขึ้น และ predicate สำหรับหยุด
2. **สร้าง harness พิสูจน์ว่ามันไว แล้วแช่แข็ง** รัน workload ที่ต่างกันเพื่อดูว่า harness แยกเคสได้ ตรวจด้วย `benchmark-checklist` และให้ harness พิมพ์จำนวน error และจำนวนงานด้วย
3. **เปิด decision log** `decision.tsv` แถวละหนึ่งความพยายาม: id, hypothesis, change, before, after, delta, tests, verdict, note (gitignore ไว้)
4. **ทุกสมมติฐานต้องระบุกลไก** เช่น "ย้าย X ออกจาก boot path เพราะ block first paint" ไม่ใช่ "ลอง memoize อะไรสักอย่าง"
5. **Loop** ทีละสมมติฐาน
   - ส่งงานให้ subagent ที่ขอบเขตแคบ แล้วรีวิว diff ถ้ามีหลายสมมติฐานที่อิสระกัน ให้แยก worktree แล้วทำขนาน
   - วัดก่อนและหลังด้วย harness ที่แช่แข็งไว้ และรัน regression gate
   - เก็บไว้เฉพาะเมื่อ metric ขยับเกิน noise และ gate ยังเขียว ไม่อย่างนั้น revert ทั้งหมด
   - หนึ่ง commit ต่อหนึ่งการปรับที่ได้ผล ใช้ `git add <files>` ห้าม `-A` และบันทึก log ทุกครั้ง
6. **ข้ามจุดที่ผลหยุดขยับ** ถ้าถูกปฏิเสธหลายครั้งติด ให้เปลี่ยนแนวทาง, รวมความพยายามที่เกือบได้ผล, อ่าน source ใหม่ หรือลองแบบที่สุดโต่งกว่า ความถูกต้องและความเรียบง่ายสำคัญกว่าตัวเลข
7. **หยุด** เมื่อ predicate เป็นจริง หรือไอเดียที่เหลือไม่คุ้มแล้ว ห้ามลดเกณฑ์ และห้ามเลิกถ้ายังมีสมมติฐานถูก ๆ ที่ยังไม่ได้ลอง
8. Opening a PR โดยเรียง commit ตามลำดับที่ได้ผล

**Reply:** metric และเป้า, baseline → ผลสุดท้าย (%), จำนวนรอบ (เก็บกับ revert), แต่ละการปรับที่ได้ผลหนึ่งบรรทัด, path ของ `decision.tsv` และไอเดียที่ดีที่สุดถ้าจะทำต่อ

### Runtime forensics
**Ownership:** You own the diagnosis. Instrument the live process, don't theorize from source. ผลลัพธ์คือการวินิจฉัย ไม่ใช่การแก้
**เหมาะกับ:** memory leak, CPU spin ตอน idle หรือ glitch ทางภาพ ในขณะที่ process ยังรันอยู่

**ขั้นตอน**
1. **เก็บสัญญาณจริง** บน surface ที่ตรงกัน ได้แก่ CPU profile สำหรับ spin, heap snapshot สำหรับ leak และ CDP trace สำหรับ glitch
2. **ย่อ artifact ให้เหลือหลักฐานชี้ขาด** เช่น function บน hot path, retainer chain จาก object ที่รั่วไปถึง GC root หรือ loop ที่ทำงานโดยไม่มี input ให้ subagent parse artifact ใหญ่
3. **พิสูจน์กลไกก่อนเชื่อ** ใส่ instrumentation ผ่าน CDP eval หรือ hotfix โค้ดสดโดยไม่ reload
4. **ชี้กลับไปที่ source:** ไฟล์, symbol และบรรทัดที่ allocate หรือ schedule
5. Throughput checkpoint: `n/a, read-only forensics`

**Reply:** สัญญาณที่เก็บ, สิ่งที่พบ, วิธีพิสูจน์กลไก, ตำแหน่งใน source และ path ของ artifact เมื่อรู้สาเหตุแล้ว ให้ส่งต่อไป Bug fix หรือ Perf issue

---

### Trace forensics
**Ownership:** You own the diagnosis from the artifact. Load it, shape it, narrow to the cause, attribute to source.
**ต่างจาก Runtime forensics:** artifact มีอยู่แล้ว (cpuprofile, `.json.gz`, spindump, heapsnapshot) ให้อ่าน ไม่ต้องรันใหม่
**เหมาะกับ:** มีคนส่งไฟล์ profile มาให้หลังเกิดเหตุ

**ขั้นตอน**
1. ระบุ format แล้วโหลดด้วยเครื่องมือที่ถูก ให้ subagent จัดการไฟล์ใหญ่
2. **แปลงให้ query ได้ก่อนอ่าน** dump ลง sqlite แถวละ sample, frame หรือ node
3. **ไล่หาสาเหตุ** query หา frame ที่ใช้เวลามากที่สุดแล้วไล่ call tree ถ้าเป็น leak ให้ไล่ retainer chain ถ้าเป็น spindump ให้หา thread ที่ค้างและเหตุผลที่รอ
4. **ชี้ไปที่ source** frame ที่ map ไป source ไม่ได้ยังนับเป็นการวินิจฉัยไม่ได้ ให้ resolve symbol หรือบอกตรง ๆ ว่า artifact ไม่มี symbol
5. **ยืนยันด้วย capture คู่** ถ้ามี before/after ให้ diff กัน ถ้าไม่มี ให้ระบุว่าเป็นสมมติฐานที่แข็งที่สุด ไม่ใช่สาเหตุที่ยืนยันแล้ว
6. ส่งการวินิจฉัยพร้อมแหล่งอ้างอิง ไม่แก้ ยกเว้นถูกขอ

---

### Visual parity
**Ownership:** You own pixel-exact equivalence. The baseline is the spec. You do not touch it. ยืนยันด้วย image diff ไม่ใช่ด้วยตา
**เหมาะกับ:** ทำ UI สอง implementation ให้เหมือนกัน หรือ migrate ระบบ styling เช่น CSS → Tailwind

**ขั้นตอน**
1. **สร้าง baseline ก่อน migrate** ใช้ harness ที่ screenshot component ปัจจุบันในทุก state ถ้าไม่มี baseline ก็อ้าง parity ไม่ได้ และนี่เป็นสิ่งที่ต้องทำก่อน ไม่ใช่งานตามหลัง
2. **ข้อห้ามกันการโกง:** ห้ามแก้ harness, ห้ามแตะ baseline และห้ามปรับโครงสร้าง component เพื่อให้ diff ผ่าน ถ้า baseline ดูผิด ให้หยุดถาม
3. **migrate ทีละ component** แยก worktree เจ้าของหนึ่งคนต่อหนึ่ง component และ migrate primitive ที่ใช้ร่วมกันก่อน
4. **ตรวจแต่ละ component ด้วย image diff** diff ที่ไม่เป็นศูนย์คือ fail ให้ตรวจ pixel ที่ต่าง แล้ววนด้วย `/loop` จน diff เป็นศูนย์
5. Opening a PR ต่อ component หรือต่อชุดที่ปลอดภัย

**Reply:** component ที่ migrate แล้ว, ผล diff ของแต่ละตัว, ตำแหน่งของ harness และสิ่งที่เหลือ

### Eval
**Ownership:** You own the experiment design. Plan, blind, run, synthesize.
**เหมาะกับ:** ทดสอบว่าการแก้ skill, โครงสร้าง หรือ prompt เปลี่ยนพฤติกรรมของ agent จริงไหม ก่อน promote

**กฎการ blind (ห้ามละเมิด)**
- คำว่า eval, test, judge, experiment, rubric, score, compare, benchmark, candidate และ arena ต้องไม่ปรากฏใน directory, ไฟล์ หรือ prompt ที่ candidate เห็น
- prompt ต้องเหมือนคำขอปกติของผู้ใช้ บอกเป้าหมาย ไม่บอกว่ากำลังวัดอะไร
- ห้ามถาม candidate ว่าใช้ skill หรือ principle อะไร ให้ประเมินจากรูปร่างของโค้ด
- ตั้งชื่อ directory ให้เหมือนโปรเจกต์จริง
- ห้ามบอกว่ามี candidate อื่น
- judge รู้ว่ากำลังตัดสิน แต่เห็นผลผ่าน label เท่านั้น ไม่เห็นชื่อโมเดล
- ถ้าเทียบ 2 variant ให้ judge คนเดียวให้คะแนนทั้งสองชุดในรอบเดียวบนสเกลเดียวกัน

**ขั้นตอน**
1. **Frame:** ระบุ variant ที่ทดสอบและพฤติกรรมที่นับว่าสำเร็จ แล้วเขียน rubric 3-6 ข้อสำหรับ judge เท่านั้น
2. **สร้างสภาพแวดล้อมที่ไม่บอกใบ้** แยก directory ต่อ candidate และวาง context ที่งานจริงจะมี
3. **เขียน prompt หนึ่งชุด** ให้เหมือนที่ผู้ใช้พิมพ์จริง
4. **ส่ง candidate N ตัว** บนโมเดลต่างกัน (ตาม arena Phase B)
5. **ส่ง judge แบบ blind** บนโมเดลต่างตระกูล (ตาม arena Phase C)
6. **ตรวจจาก transcript ไม่ใช่รายงานของ candidate** ดูว่า candidate เปิดไฟล์อะไรจริง
7. **อ่านผลทุกชิ้นเอง** แล้วเทียบกับ judge ถ้าไม่ตรงกัน แปลว่ามีโมเดลที่ลำเอียง หรือ rubric กำกวม

**Reply:** variant ที่ทดสอบ, rubric, บันทึกของแต่ละ candidate, verdict ของ judge, ข้อสรุป และข้อเสนอว่าจะ promote หรือไม่

### Babysit (playbook)
**Ownership:** You own the merge frontier. Declare a mode, clear one PR at a time, stop where the human's call begins. ใน poteto-mode ให้ใช้ playbook นี้แทน skill `babysit`
**เหมาะกับ:** "babysit this", "get it green", "address the review-bot comments" หรือ "check on PR X" โดยเริ่มเมื่อผู้ใช้ขอ ไม่ใช่ทันทีที่เปิด PR

**4 โหมด (ต้องประกาศก่อนเริ่ม poll)**
| โหมด | ใช้เมื่อ |
|---|---|
| `drive` (ค่าเริ่มต้น) | วนจนพร้อม merge |
| `background` | triage โดยไม่ block ใช้ตอนแผนยังทำอยู่ |
| `threads-only` | ตอบ review comment อย่างเดียว |
| `check` | ดูสถานะหนึ่งรอบแล้วรายงาน |

**ขั้นตอน**
1. ประกาศโหมดและเลือก forge (`gh` หรือ Origin)
2. **ทำเฉพาะ merge frontier** คือ PR ล่างสุดที่ยังไม่ merge PR ที่อยู่สูงกว่าแค่อ่านและรวบรวมไว้
3. หนึ่ง babysitter ต่อหนึ่ง stack
4. **ห้ามเปลี่ยนโครงสร้าง stack** ห้าม retarget, rebase หรือ force-push ให้รายงานขึ้นไปแทน
5. **ลำดับ:** conflict → review thread → CI และรวมการแก้ไว้ใน push เดียว conflict ให้รายงาน ไม่ต้องแก้เอง
6. **เชื่อ verdict ของ forge** ไม่ใช่รายการ check ที่เขียว บน GitHub ใช้ watcher `watch-pr` (verdict: `READY`, `WAITING`, `ADVANCE`, `COMPLETE`, `BLOCKER`)
7. **แยกประเภท CI ก่อน retrigger** ถ้าเป็น flake ให้ build ใหม่หนึ่งครั้ง ถ้า fail เหมือนเดิมแปลว่าไม่ใช่ flake ถ้า fail ในโค้ดที่ diff ไม่ได้แตะ ให้สงสัยว่า base เก่า
8. **อ่าน comment ของ bot อย่างสงสัยไว้ก่อน** แก้ปัญหาจริงด้วย red-first proof ใน PR ล่างสุดที่เป็นเจ้าของโค้ดนั้น
9. **หยุดที่จุดที่ต้องให้คนตัดสิน** babysit ไม่มีสิทธิ์ merge การ merge ต้องมาจากคำขอที่ชัดเจน แล้วส่งต่อให้ Shipping

**Reply:** โหมด, frontier และสถานะ, ตาราง 4 คอลัมน์จาก watcher, สิ่งที่แก้และสิ่งที่ dismiss พร้อมเหตุผล, สิ่งที่ค้าง และสิ่งที่ต้องให้คนตัดสิน

### Shipping
**Ownership:** You own what lands. Land one verified PR at a time, then confirm its outcome before advancing. ต้องได้รับอำนาจในการ land จากผู้ใช้
**เหมาะกับ:** "land this stack" หรือ "ship it" หลังจาก babysit จนเขียวแล้ว

**ขั้นตอน**
1. **เลือก forge และเก็บ dependency chain** ทุก branch, head SHA และ base SHA จากล่างขึ้นบน
2. **ตรวจแต่ละ PR อย่างอิสระ** subagent หนึ่งตัวต่อ PR ใช้ worktree ของตัวเอง ขับ surface จริงเทียบ parent กับ head แล้วให้ผล `PASS`, `PASS+NOTES` หรือ `FAIL` **ผู้ตรวจต้องไม่ใช่คนเขียนโค้ด** CI ที่เขียวกับ bot ที่ approve ใช้แทนไม่ได้ บันทึก head SHA, base SHA และ `git patch-id`
3. **หาชุด PR ที่ verify ต่อเนื่องกัน** ไล่จาก PR ล่างสุด แล้วหยุดที่ตัวแรกที่ไม่ผ่าน PR ลูกที่ผ่านแต่อยู่บน parent ที่ไม่ผ่าน ยัง land ไม่ได้
4. **ยกเลิก merge ที่ค้างอยู่ก่อนแก้ chain** (`ship-pr cancel-pending`)
5. **เตรียมเฉพาะ PR ล่างสุด** rebase แล้ว push ด้วย lease และ retarget ไปที่ trunk
6. **ประเมินหลักฐานใหม่** head หรือปลายทางที่เปลี่ยนทำให้ผลเดิมใช้ไม่ได้ ใช้ patch-id และการ build ซ้ำเพื่อแยก noise
7. **Merge โดยให้ service บังคับ head** `gh pr merge --squash --match-head-commit <verified-head>`
8. **ตั้ง auto-merge ได้เฉพาะเมื่อมี gate ที่บังคับได้จริง** ห้ามแก้ protection settings เพื่อให้ผ่าน
9. **เฝ้า frontier** ด้วย `watch-pr --queued-stack` ภายใต้ `/loop`
10. **ยืนยันการ land ก่อนไปตัวถัดไป** อ่านสถานะ merged และตรวจว่า merge commit อยู่ในประวัติของปลายทางจริง ถ้าแค่ queued ยังไม่นับว่า merge แล้ว
11. **หยุดที่ PR สุดท้ายที่ verify แล้ว** แล้วรายงานว่า PR ถัดไปต้องการอะไร

**หลักออกแบบที่น่าเรียนรู้:** "Green is not safe" คือ CI เขียวไม่ได้แปลว่าปลอดภัย และ verdict ผูกกับ SHA ถ้า SHA เปลี่ยน ต้องตรวจใหม่

### Autopilot-full
**Ownership:** You own the verdicts, never the PRs. เจ้าของหนึ่งคนดูแล PR หนึ่งตัวตั้งแต่ build จนพร้อม merge และไม่มีอะไร merge ได้ถ้าไม่มีทั้ง swarm verdict ที่สะอาดและการกด merge ของผู้ใช้เอง
**เหมาะกับ:** "autopilot this queue" หรือ "full autopilot" สำหรับคิวของ PR ที่อิสระต่อกัน

**ขั้นตอน**
1. **แยกงานของผู้ใช้ไว้ และแถลงก่อนรอ** ถ้าผู้ใช้ขอให้อธิบายแผน ให้อธิบายแล้วหยุด เริ่มทำเมื่อได้ go ชัดเจนเท่านั้น แล้วเขียนเป้าหมายลง standing orders
2. **เจ้าของหนึ่งคนต่อ PR** ใช้ subagent เบื้องหลังใน worktree ของตัวเอง ดูแลตั้งแต่ build → PR → babysit → พร้อม merge และเริ่ม decision trail ตั้งแต่ต้น
3. **ขนานจริงและไม่ทำ stack** PR อิสระแตกจาก main โดยตรง และทำต่อกันเฉพาะงานที่ทับกันจริง
4. **swarm-verify ทุกรอบก่อน merge** เริ่มที่ head SHA ตอนโค้ดพร้อม และทุกครั้งที่ push แล้ว patch เปลี่ยน
5. **verdict สะอาดแล้วส่งต่อ** head ต้อง rebase บน trunk ล่าสุดและผ่าน CI แล้วเจ้าของคนใหม่รับงานถัดไป
6. **ชั้นบนสุดเป็นผู้ countersign** การขยายค่า gate หรือ budget ที่ถูก pin ไว้ ต้องมี countersign หลังมีหลักฐานจากผู้ตรวจ
7. **หยุดทันทีเมื่อผู้ใช้สั่ง** ทุกเจ้าของได้คำสั่งให้หยุดเขียนทันที

### Autopilot-stack
**Ownership:** You own the stack, never the landing. build และ verify คิวงานแบบอัตโนมัติ แล้วส่ง stack เส้นเดียวให้ผู้ใช้รีวิวและ land เอง
**เหมาะกับ:** "stack them, don't ship" หรือ "build the stack, I'll land it"

**ขั้นตอน**
1. ใช้ loop ของเจ้าของแบบเดียวกับ Autopilot-full
2. **audit ทุกชั่วโมง** ด้วย `/loop` แบบ dynamic และอ่าน playbook กับ standing orders ใหม่จาก disk ทุกรอบ
3. **รอ gate ของผู้ใช้** แถลงแล้วรอ go และหยุดทันทีเมื่อสั่ง
4. **verify ทุกรอบ** เจ้าของรายงาน STACK-READY พร้อม head SHA แล้วบันทึก patch-id
5. **verdict สะอาดแล้วต่อท้าย stack แต่ไม่ ship** ไม่มีใคร merge หรือตั้ง auto-merge
6. **topology มีผู้เขียนคนเดียว ส่วน build ทำขนานได้** เจ้าของ push เฉพาะ branch ตัวเอง และมีแค่ root ที่ rebase หรือ retarget
7. **root ดูดซับ drift แล้ว verify ใหม่** rebase จากล่างขึ้นบน ซึ่งทำให้ verdict ที่ SHA เก่าใช้ไม่ได้ จึงต้องใช้กฎ patch-id
8. **ส่งมอบ chain** ทุก PR มี verdict อยู่ใน body หรือ comment

**เลือกระหว่างสองแบบ:** ใช้ Autopilot-full เมื่อ PR อิสระต่อกันและได้รับอำนาจ merge ใช้ Autopilot-stack เมื่อผู้ใช้ต้องการรีวิวก่อน land, งานผูกกัน หรือไม่ได้ให้อำนาจ merge

### Multi-phase or multi-PR plan
**Ownership:** You own the plan, not the code. แผนคือ checklist ที่เจ้าของงานทำทีละช่อง และผู้ใช้ตรวจได้จากหลักฐาน **ผลลัพธ์คือแผน ห้าม implement**
**เหมาะกับ:** งานหลาย phase หรือหลาย PR ที่ต้องวางแผนก่อนให้ Orchestrate หรือ Autopilot ทำ

**ขั้นตอน**
1. ถ้าเป็นงาน 1-2 ไฟล์ที่วิธีทำชัดเจน ให้ข้ามการทำแผน บอกเหตุผล แล้วหยุด
2. **ตอบคำถามที่ค้างด้วย prototype ก่อนเขียนแผน** เก็บ branch, SHA และ screenshot ไว้ใน Appendix A ถามผู้ใช้เฉพาะเรื่องความชอบหรือการตัดสินใจเชิงผลิตภัณฑ์
3. สำรวจผ่าน subagent ที่คืน file pointer, convention, คำสั่ง test และ entry point โดยไม่ dump เนื้อหา
4. **คัด skeleton ลงไฟล์แผน** แล้วกรอกทุกช่อง (ค่าเริ่มต้นเก็บที่ `~/.claude/orchestrate/<slug>/docs/`)
5. เขียนด้วย `technical-writing` + `unslop` ส่วน body เป็น how-to และ appendix เป็น explanation หรือ reference
6. **รัน `check-plan.mjs`** แล้วแก้ทุกบรรทัดที่มันแจ้ง
7. ส่ง path ของแผนกับ output ของ script แล้วหยุด เริ่มทำงานเมื่อผู้ใช้สั่ง go เท่านั้น

**กฎการ verify:** test อย่างเดียวไม่พอ PR จะนับว่า verify แล้วก็ต่อเมื่อช่อง unit, live และ perf ถูกติ๊กครบ

**โครงสร้างไฟล์แผน (skeleton)**
- สรุปไม่เกิน 10 บรรทัด และหัวข้อ "How to read this"
- **Program checklist:** Arm the program (แถลงแล้วรอ go, standing orders, ไฟล์ที่ต้องอ่านใหม่ทุก tick, hourly audit ด้วย `/loop`), Spawn owners (dependency graph, ขอบเขตไฟล์, review gate), PR mechanics, Verdict and merge (swarm: gates lane + 10 live lanes + perf lane + audit) และ Boot recipe
- **หนึ่ง section ต่อ PR:** Depends on, Files, Build, You see, Verify unit, Verify live (10 lanes พร้อม screenshot และ predicate), Verify perf (metric, probe, baseline, rule), Review gate (screenshot + วิดีโอ 30-60 วินาที) และ Merge

### Worktree and simulator cleanup
**Ownership:** You own the disk and the safety gate. การลบย้อนกลับไม่ได้ ทุกขั้นจึงกันไม่ให้ลบของที่ยังใช้อยู่หรือยังมีงานที่ไม่ได้ commit
**เหมาะกับ:** "what's using my disk", "clean up worktrees" หรือ "delete old simulators"

**ขั้นตอน**
1. **Snapshot และ audit** บันทึก `df -h /` แล้วรัน `worktree-audit.mjs` ซึ่งอ่าน path จาก `git worktree list` ไม่ให้พิมพ์เอง แล้วจัดกลุ่มตามขนาด อายุ สถานะ merge และงานที่ยังไม่ commit
2. **กลุ่มที่ script จัดเป็นแค่คำแนะนำ ไม่ใช่การอนุญาต** แชตที่ pin ไว้และแชตที่ยังทำงานอยู่คือแหล่งความจริง เคยมีกรณีที่ script ตีว่า `safe` ทั้งที่ผู้ใช้ pin worktree นั้นไว้
3. **ตรวจการใช้งานก่อนลบ** ให้ subagent อ่าน transcript ว่าแชตไหนยังใช้ worktree ไหน
4. **หยุดถามก่อนจะเสียงานที่ไม่ได้ commit** `wip:N` ให้แสดง diff แล้วรอการตัดสินใจ ส่วน `scratch:N` ลบได้ แต่ต้องบอกชื่อไฟล์
5. **ลบชุดที่ยืนยันแล้ว** ด้วย `git worktree remove --force` ตามด้วย `git worktree prune` branch ref ยังอยู่ จึงไม่เสีย commit
6. **Simulator และส่วนอื่น** `xcrun simctl delete unavailable`, ลบ runtime เก่า, DerivedData และ cache

**ข้อสังเกต:** เป็น playbook เดียวที่ลบ state ของผู้ใช้โดยไม่มี code review ช่วยดัก gate ในขั้นตอนจึงทำหน้าที่แทนการรีวิว
**Reply:** `df -h /` ก่อนและหลัง, worktree ที่ลบ และเหตุผลของตัวที่เก็บไว้
