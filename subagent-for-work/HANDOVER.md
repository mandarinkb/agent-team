# HANDOVER — ชุด teammate ของ icrm-share (ส่งไปปรับกติกา แล้วส่งกลับ)

ไฟล์นี้อยู่ที่ราก zip · อ่านก่อนทำอย่างอื่น

## 1. นี่คืออะไร
ชุด "ทีม AI" ที่ใช้ทำ ticket ใน repo `icrm-share` (Go API ของแพลตฟอร์ม iCRM): lead + 3 role (`backend`, `qa`, `spec-reviewer`) และ role เสริม `analyst` พร้อม workflow และแบบฟอร์ม
**ในชุดนี้มีเฉพาะ "กติกาและโครงทีม" — ไม่มีโค้ดของโปรเจกต์ ไม่มี ticket ไม่มีรายงานรีวิว ไม่มีไฟล์ `.env*` และไม่มี `settings.local.json`**

## 2. ในชุดมีอะไร
| path | คืออะไร |
|---|---|
| `.claude/agents/analyst.md` | หาหลักฐานแบบอ่านอย่างเดียว ไม่แก้โค้ด |
| `.claude/agents/backend.md` | implement ticket (Go, test-first) เฉพาะ `public/` `private/` `utility/` ไม่ตัดสินงานตัวเอง ไม่ commit |
| `.claude/agents/qa.md` | เขียน Bruno จาก ticket (ไม่อ่านโค้ด) แล้วรันเมื่อ lead สั่ง "GO" |

| `.agents/README.md` | ภาพรวมการติดตั้ง + สิ่งที่ยังไม่ได้ทำ |

> **ตั้งใจไม่รวม `.claude/skills/`** — role บางตัว (เช่น `qa.md`) อ้างถึง skill `local-run` และ `bruno-regression` ซึ่ง**ไม่อยู่ในชุดนี้** ปลายทางจะเปิดอ่านไม่ได้ ให้ถือว่าชื่อ skill เหล่านั้นเป็นเพียงข้อมูลอ้างอิง อย่าแก้หรือลบการอ้างถึงเอง และถ้าต้องตัดสินใจเกี่ยวกับกติกาที่ผูกกับ skill ใด ให้จดเป็นคำถามใน `CHANGELOG.md` ให้ฝั่งต้นทางตอบ

## 3. ภาพรวมการทำงาน (ย่อ)
ลำดับของ 1 ticket (รายละเอียดเต็มใน `.agents/workflows/ticket.md`):
1. **lead** อ่าน ticket + spec แล้วสรุปแผน/ไฟล์ที่จะแตะ/ข้อสงสัย **รอ user ยืนยัน** (ยังไม่สร้างทีม)
2. หลังยืนยัน: **backend** implement test-first ขนานกับ **qa** เขียน Bruno จาก ticket (qa ไม่อ่านโค้ด backend)
3. backend แจ้ง "implemented" → lead เทียบ `git status` กับรายการไฟล์ → **spec-reviewer** ตรวจ diff ทีละ AC (read-only) ขนานกับ **qa** รัน local เมื่อได้ "GO"
4. ไม่ผ่าน: fix item ส่งให้ backend ผ่าน lead ไม่เกิน 3 รอบต่อประเด็น เรื่องที่ต้องให้ user ตัดสินส่งเป็น decision request
5. ปิดงาน: lead รัน `go build`/`go test` เอง อัปเดต ticket เสนอ commit message **ไม่ commit/push เอง**

หลักคิดของชุดนี้: **ผู้ตรวจ ≠ ผู้เขียน** · หลักฐานต้องมี `file:line` · AC ที่ตรวจไม่ได้ต้องลงเป็น UNVERIFIED ไม่ใช่ผ่าน · เรื่องที่เปลี่ยน contract/scope ต้องถาม user

## 4. ข้อจำกัดของเครื่อง/session ปลายทาง
- ชุดนี้อ้างถึงสิ่งที่อยู่ใน repo จริง (`AGENTS.md`, `.scratch/<slug>/issues/*.md`, `bruno/`, `public/` `private/`, `.icrm-context/`) ซึ่ง**ไม่ได้อยู่ในชุดนี้** → ที่ปลายทางทำได้เฉพาะ **อ่านและปรับกติกา (ข้อความในไฟล์ `.md`/แบบฟอร์ม)** ไม่ต้องพยายามรัน Go/Bruno/ทดลองทำ ticket จริง
- Claude Code จะค้นเจอ role เมื่อเปิดใน "โฟลเดอร์ที่มี `.claude/agents/`" — แตกไฟล์ลงโฟลเดอร์ว่างโฟลเดอร์หนึ่ง แล้วเปิด Claude Code ที่นั่น ตรวจด้วย `/agents` ว่าเห็น 4 role
- ห้ามนำข้อมูลภายในบริษัทอื่นๆ มาแปะเพิ่ม (ticket, ข้อมูลลูกค้า, ค่า env, secret) ชุดนี้ตั้งใจให้ไม่มีข้อมูลเหล่านั้น

## 5. ข้อควรระวังเวลาแก้ไฟล์ role/workflow
- **อย่าลบหรือเปลี่ยนชื่อ key ในหัวไฟล์ role** (`name`, `description`, `disallowedTools`, `model`) — เป็นตัวกำหนดว่า Claude Code โหลด role ได้และ role ไหนแก้ไฟล์ไม่ได้ (`analyst`, `spec-reviewer` ปิด `Edit`/`NotebookEdit`)
- ชื่อไฟล์ role ต้องตรงกับ `name:` ในหัวไฟล์ (`backend.md` ↔ `name: backend`) และ workflow/README อ้างถึงชื่อเหล่านี้ ถ้าเปลี่ยนชื่อต้องแก้ทุกที่
- path ที่อ้างถึง (`.agents/templates/...`, `.scratch/<slug>/reviews/...`) ต้องยังตรงกับของจริงใน repo ต้นทาง
- แก้กติกาแล้ว **จดรายการที่แก้พร้อมเหตุผลลง `CHANGELOG.md`** (สร้างใหม่ที่รากชุดนี้) เพื่อให้ฝั่งต้นทางตรวจรับได้ทีละข้อ
- กติกาในชุดนี้บางข้อเกิดจากเหตุการณ์จริง (ระบุ "บทเรียน ticket NN" ไว้ในไฟล์) ก่อนลบหรือผ่อนกติกาข้อใด ให้ถามเหตุผลที่มาก่อน

## 6. หัวข้อที่ฝั่งต้นทางอยากให้พิจารณา (ข้อสังเกตจากการใช้งานจริง ไม่ใช่คำสั่ง)
1. ไม่มีข้อห้ามอ่าน/พิมพ์เนื้อหาไฟล์ `.env*` ใน role ใดเลย (มีแค่ "ห้ามพิมพ์ secret") — เคยพลาดจริง: สั่ง `tail` ไฟล์ env แล้วค่า secret หลุดลง transcript ควรมีกฎ "ตรวจ env ได้แค่ `grep -c '^NAME=' file` พิมพ์จำนวน" ในทุก role
2. `qa.md` ห้าม "สร้าง member ต่อรัน / ทดสอบเฉพาะโฟลเดอร์ใหม่" แต่ `Member Session Fixture` ต้องรันคู่กับ `ICRM Journey` ซึ่งสร้าง member ถาวรทุกรอบ → ต้องขอ user อนุมัติทุกครั้ง ควรเขียนข้อยกเว้นและเงื่อนไขให้ชัด
3. `qa.md` ห้ามแก้ Bruno request เดิม แต่บางครั้งต้องแก้เล็กน้อยเพราะ contract เปลี่ยน (เช่นเพดาน `pageSize`) → ควรมีขั้นตอนขออนุมัติที่ชัดเจน
4. `spec-reviewer.md` ระบุให้ทดสอบใน `git clone` สำเนา แต่ในทางปฏิบัติใช้ `rsync` สำเนานอก repo ผลเท่ากัน — ควรให้ข้อความตรงกับที่ทำจริง
5. ความเสี่ยงที่ backend ตัดสินใจเองในจุดที่ ticket เงียบแล้วรายงานทีหลัง (เปลี่ยนค่าใน edge case) — ควรกำหนดเส้นแบ่งว่าอะไรต้องหยุดถามก่อน อะไรเลือกค่าปลอดภัยไปก่อนได้
6. ข้อความถึง teammate ไม่มีแบบฟอร์มสำหรับ "HOLD / GO / คำสั่งแทนที่" (มีเฉพาะใน `ticket.md`) — ควรมีแม่แบบสั้นๆ
7. `.agents/README.md` ระบุว่า "ยังไม่ใช่ Agent Teams (ไม่คุยกันเอง)" แต่ workflow ปัจจุบันมี teammate คุยกันผ่านข้อความ — ควรปรับให้ตรงกัน

## 7. วิธีส่งกลับ
1. แก้เสร็จ ให้บีบ **ทั้งโฟลเดอร์ชุดนี้ (รวม `CHANGELOG.md`)** เป็น zip ส่งกลับ
2. ฝั่งต้นทางจะเทียบกับ `MANIFEST.sha256` เพื่อดูว่าไฟล์ไหนเปลี่ยน แล้ว `diff -ru` ทีละไฟล์ก่อนคัดลอกกลับเข้า repo
3. **ห้ามลบไฟล์ใน `MANIFEST.sha256` หรือแก้ไฟล์นี้** — ถ้าจะเพิ่มไฟล์ใหม่ ให้ลงใน `CHANGELOG.md` ด้วย
