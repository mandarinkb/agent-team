# Workflow: implement ticket ด้วยทีม (lead + backend + qa + spec-reviewer)

ตามขั้นตอนที่ผู้ใช้ทำอยู่: **implement → สร้าง Bruno → รัน local ทดสอบด้วย Bruno → ไม่ผ่านให้แก้แล้วทดสอบใหม่ → ผ่านหมดแล้วอัปเดต ticket + commit message** (commit เมื่อผู้ใช้สั่งเท่านั้น)

## กลไก: subagent ทีละขั้น (ไม่ใช่ Agent Teams)
- ทุก role เป็น **subagent** ที่ lead spawn ด้วยเครื่องมือ Agent (`subagent_type` = ชื่อ role) **ไม่ตั้ง `name`** — ถ้าเครื่องเปิด `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` ไว้ การตั้งชื่อจะทำให้กลายเป็น teammate
- **หนึ่ง spawn = หนึ่งขั้น** subagent ทำขั้นนั้น เขียนไฟล์ รายงาน lead แล้วจบ ไม่มีตัวที่ค้างรอข้อความ จึงไม่ต้องมี HOLD / GO / shutdown
- **ไม่มีการคุยกันเองระหว่าง role** ทุกการส่งต่อผ่าน lead: lead อ่านรายงาน แล้ว spawn ขั้นถัดไปพร้อม brief (`.agents/templates/brief.md`)
- subagent รู้แค่สิ่งที่อยู่ใน brief และในไฟล์ brief จึงต้องระบุ ticket, รอบ, path, รายการไฟล์ที่อนุมัติ, contract และคำตัดสินของผู้ใช้แบบคำต่อคำ — อ้าง path แทนการแปะเนื้อหายาว
- ขั้นที่ไม่ขึ้นต่อกันให้ spawn ใน message เดียวกันแบบ `run_in_background: true` แล้วรอผลทั้งคู่ ห้ามเดาหรือเขียนรายงานแทน subagent ที่ยังไม่ส่งผล
- **หลักฐานทุกรอบ:** ทุกขั้นที่ทดสอบหรือตรวจ เขียนหลักฐานลง `.scratch/<feature-slug>/reviews/<ticket>/r<n>/` (`n` = รอบ) ผลดิบจากเครื่องมือ (log) คือหลักฐาน ข้อความที่ subagent เขียนเป็นแค่สารบัญที่ชี้ไปหา log · บันทึก output ลงไฟล์ด้วย `> file 2>&1` แล้วอ่านเฉพาะส่วนที่ต้องใช้ ไม่พิมพ์ output เต็มเข้า context · รายงานถึง lead อ้าง path ไม่แปะผล · โฟลเดอร์ `reviews/` ถูก gitignore ผู้ใช้อ่านแล้วลบทิ้งได้
- **บันทึกการตัดสินใจ `log.tsv`** (ในโฟลเดอร์ `reviews/<ticket>/`, lead เขียนคนเดียว เพิ่มต่อท้ายอย่างเดียว ห้ามแก้แถวเก่า): หนึ่งแถวต่อการตัดสินใจ คอลัมน์ `ts	step	decision	why	evidence	result` คั่นด้วย tab ทุกช่องบรรทัดเดียว ไม่มี tab ข้างใน · `evidence` เป็น pointer (path, `file:line`, ชื่อ fix item) ไม่ใช่ข้อความยาว · `result` เช่น `PASS`, `FAIL`, `BLOCKED`, `open`, `user: "<คำต่อคำ>"` · เขียนเมื่อ: spawn แต่ละขั้น, ส่ง fix item, ได้คำตัดสินของผู้ใช้, หยุดหรือ BLOCKED, retry ตามประเภท, เปลี่ยน subagent ที่ติด, ปิดงาน · ใช้ `printf '%s\t%s\t%s\t%s\t%s\t%s\n' ... >> log.tsv`
- **สถานะ `progress.md`** (ในโฟลเดอร์ `reviews/<ticket>/`): lead เขียนทับหลังจบทุกขั้น เป็นตารางเดียวกับที่สรุปให้ผู้ใช้ ได้แก่ ขั้น / role / สถานะ / รอบ / ไฟล์หลักฐาน, decision request ที่ค้าง และขั้นถัดไป ใช้ตอนทำต่อเมื่อ session หลุด (หัวข้อ "ทำต่อเมื่อ session หลุด")

## บทบาท
| ใคร | ทำอะไร | ห้าม |
|---|---|---|
| **lead** (session หลัก) | อ่าน ticket + spec, สรุปแผน/ไฟล์ให้ผู้ใช้ยืนยัน, spawn แต่ละขั้นพร้อม brief, ส่งต่อ fix item, อัปเดต Status + `## Comments` ของ ticket, เขียน commit message, รอผู้ใช้สั่ง commit | เขียนโค้ดแทน backend, ตัดสินแทนผู้ใช้ |
| **backend** | implement (test-first) เฉพาะโค้ดใน `public/` `private/` `utility/` | แตะ `bruno/`, ตัดสินงานตัวเอง, commit |
| **qa** | เขียน Bruno จาก ticket แบบ blind ขนานกับ backend แล้ว (ใน spawn แยก) รัน local เฉพาะโฟลเดอร์ของ ticket | แก้โค้ด production, อ่านโค้ดที่ backend เขียนก่อนเขียน Bruno เสร็จ |
| **spec-reviewer** | ตรวจ diff เทียบ ticket ทีละ AC พร้อม `file:line` และตรวจคุณภาพ test/Bruno | แก้โค้ด |
| **analyst** (ไม่บังคับ) | หาหลักฐานก่อน implement เมื่อ ticket ยังมีข้อสงสัย | แก้โค้ด |

## ลำดับ
1. **lead:** อ่าน `AGENTS.md`, ticket, spec section, upstream design → สรุป "จะทำอะไร + **รายการไฟล์ที่จะแตะ** + ข้อสงสัย" → **รอผู้ใช้ยืนยัน** (ขั้นนี้คือ gate; ยังไม่ spawn ใครก่อนยืนยัน) รายการไฟล์ที่ผู้ใช้ยืนยันคือ scope ที่ใส่ใน brief ของ backend
   - สรุปขั้นนี้ต้องมีหัวข้อ **"AC ที่ทีมพิสูจน์ใน session นี้ไม่ได้"** — AC ที่ต้องรันบน env จริง (dev / sit / test), ต้อง deploy ก่อน, ต้องมีข้อมูลที่ยังไม่มี หรือขึ้นกับระบบนอก workspace — พร้อมทางเลือกให้ผู้ใช้ตัดสินตั้งแต่ต้น (ปิดแบบ partial พร้อมบันทึก UNVERIFIED / ขอสิทธิ์ / แยก ticket) ไม่รอให้ spec-reviewer ตีเป็น FAIL ตอนท้าย (บทเรียน ticket 06 AC ข้อ 7 "ผ่านบน dev")
   - ถ้า ticket ยังมีข้อสงสัยที่ต้องหาหลักฐาน: spawn **analyst** ก่อนสรุป แล้วใช้ `investigation` ประกอบแผน
   - **บันทึก snapshot ตอนเริ่ม:** ก่อน spawn ขั้นแรก lead รัน `git status --short` และ `git log --oneline -1` เก็บลงไฟล์ชั่วคราวนอก repo (เช่น scratchpad) ใช้เทียบทีหลังว่าไฟล์ไหนเป็นงานที่มีอยู่ก่อน (ของผู้ใช้) และไฟล์ไหนทีมเพิ่ม — ไม่ใช้ความจำ
2. **ขนาน (spawn พร้อมกันแบบ background, แตะคนละที่):**
   - **backend** — brief: ticket, รายการไฟล์ที่ผู้ใช้ยืนยัน, รอบที่ 1, โฟลเดอร์หลักฐาน `r1/` → implement (ข้อ backend 1-7) เขียน `r1/backend-tests.md` แล้วรายงาน "implemented" + รายการไฟล์ + contract ที่สร้างจริง
   - **qa (เขียน)** — brief: ticket, โฟลเดอร์ `bruno/Regression/<Folder>/`, "ห้ามอ่านโค้ดของ backend, ห้ามรัน" → เขียน Bruno + syntax check แล้วรายงาน
   - **lead เทียบไฟล์ก่อนส่งต่อ:** เมื่อรายงานของ backend มาถึง ให้ lead รัน `git status --short` เทียบกับรายการไฟล์ที่ผู้ใช้ยืนยันเอง ไม่เชื่อแค่คำว่า "diff matches the list" — ไฟล์ที่เกินรายการ (เช่น จาก `gofmt -w` ทั้งโฟลเดอร์) ให้หยุดก่อน spawn qa / spec-reviewer แล้วถามผู้ใช้ว่าจะกู้ (`git checkout --` เฉพาะไฟล์ที่ยืนยันแล้วว่าไม่มีงานของผู้ใช้ปน — เทียบกับ `git status` ตอนเริ่ม session) · การกู้ถือเป็นโค้ดเปลี่ยน ต้องให้ qa รันใหม่และให้ spec-reviewer ตรวจ delta (ข้อ 5 ของกติกาการประสานงาน)
3. **qa (เทียบ contract):** lead spawn qa พร้อม contract ที่ backend รายงาน → qa ตรวจว่า Bruno ตรงกับ contract ที่ ticket กำหนด (ไม่ใช่ตามโค้ด) · ความต่างระหว่าง contract ใน ticket กับที่ backend ทำ = fix item หรือเรื่องให้ผู้ใช้ตัดสิน · ขั้นนี้รวมกับขั้น 4 ใน spawn เดียวได้ถ้าไม่มีความต่าง
4. **ขนาน (spawn พร้อมกันแบบ background):**
   - **spec-reviewer** ตรวจ diff (read-only) เขียนผลที่ `r<n>/spec-review.md`
   - **qa (รัน)** รันเฉพาะโฟลเดอร์ของ ticket ที่ local (skill `local-run`, test OTP, อ่าน DB อย่างเดียว) — **การ spawn ขั้นนี้คือสัญญาณ GO** lead spawn เมื่อโค้ดนิ่งแล้วและไม่มี decision request ค้างที่เกี่ยวข้องเท่านั้น · รันใหม่ (spawn ใหม่) ทุกครั้งที่โค้ดเปลี่ยน (หยุดและเริ่ม server ใหม่ ไม่ใช้ binary เก่า) · qa ต้องหยุด server และ `bru` ที่ตัวเองเปิดก่อนรายงาน · หลักฐานของรอบนี้: `r<n>/qa.md`, `r<n>/bruno.log` และ `r<n>/git-status.txt` (สถานะไฟล์ตอนที่รัน)
5. **ไม่ผ่าน:** ผู้พบเขียน fix item (`.agents/templates/fix-task.md`) ในรายงาน/ไฟล์ review → lead spawn **backend ตัวใหม่** พร้อม path ของ fix item, รอบที่ และโฟลเดอร์หลักฐานของรอบใหม่ (`r<n+1>/`) → backend แก้ → lead spawn qa/spec-reviewer ตรวจใหม่ · **ไม่เกิน 3 รอบต่อประเด็น** (lead นับรอบจากไฟล์ review/fix item ไม่ใช้ความจำ) รอบที่ 4 หรือสาเหตุเดิมซ้ำ 2 รอบ → หยุดแล้วถามผู้ใช้
6. **ผ่านหมด:** qa พิสูจน์ว่า Bruno แดงได้ (หรือบันทึกเป็นช่องโหว่) · lead รัน `go build ./...` + `go test ./...` เอง 1 ครั้งบนโค้ดสุดท้าย (ไม่เชื่อรายงานของ subagent) เก็บผลทั้งหมด (stdout + exit code) ลงไฟล์ชั่วคราวนอก repo แล้วอ่านจากไฟล์ — ไม่รันซ้ำเพื่อนับหรือหาบรรทัด FAIL รันใหม่เฉพาะเมื่อโค้ดเปลี่ยนหลังรอบนั้น · เช็ก `git status` ไม่มีไฟล์ชั่วคราว (เทียบกับ snapshot ตอนเริ่ม)
   - **โค้ดเปลี่ยนหลัง qa รันรอบสุดท้ายไหม:** lead รัน `git status --short` และ `git diff --stat` แล้วเทียบกับ `r<n>/git-status.txt` ของรอบสุดท้ายที่ qa รัน เขียนผลลง `evidence.md` ว่า "ไม่มี" หรือ "มี: <ไฟล์>" · ถ้ามี ให้ spawn qa รันใหม่ หรือบันทึกใน `evidence.md` และ `## Comments` ว่าส่วนนั้นไม่ได้ทดสอบ ห้ามข้ามข้อนี้
7. **lead:** อัปเดต ticket (ติ๊ก checklist, Status, `## Comments` พร้อม `file:line` และรายการ UNVERIFIED) + เสนอ commit message · **รอผู้ใช้สั่ง commit**; ไม่ push
   - **หน้าหลักฐาน:** lead เขียน `.scratch/<feature-slug>/reviews/<ticket>/evidence.md` จาก `.agents/templates/evidence.md` โดยอ่านแค่ `r*/qa.md`, `r*/spec-review.md` และ `r*/backend-tests.md` ไม่อ่าน log เต็ม (อ้าง path แทน) แล้วบอก path นี้กับผู้ใช้ก่อนขอให้สั่ง commit
   - **ปิดงาน:** subagent จบเองหลังรายงาน ไม่ต้องส่ง shutdown · ก่อนรายงานว่าปิดงาน lead ตรวจว่าไม่มี subagent แบบ background ที่ยังไม่ส่งผล และไม่มี server / `bru` ค้าง (`ps` หา process ที่ qa เปิด) — ถ้ามี ให้บอกผู้ใช้ตรงๆ ไม่รายงานว่า "ปิดแล้ว" จากการคาดเอา
   - **เสนอ retro:** ถ้า ticket นี้วนแก้ตั้งแต่ 2 รอบขึ้นไป หรือมีการทำผิดกติกา (เช่น qa รันก่อน `Step: 4 run`, แตะไฟล์นอกรายการ) ให้ lead บอกผู้ใช้ว่า "ticket นี้ควรรัน `/retro`" พร้อมเหตุผลหนึ่งบรรทัด และบอกว่า retro ควรอ่าน `log.tsv` กับ `progress.md` ก่อน แล้วเปิด transcript ของ subagent เฉพาะจุดที่ log ชี้ · **ห้ามรันเอง** ผู้ใช้เป็นคนตัดสินว่าจะรันหรือไม่

## กติกากลาง
- ผู้ตรวจ ≠ ผู้เขียน: backend ไม่ตรวจงานตัวเอง, qa ไม่แก้โค้ด, spec-reviewer ไม่แก้อะไร
- คำกล่าวอ้างไม่ใช่หลักฐาน: "เสร็จ/ผ่านแล้ว" นับเมื่อคนอื่นรันซ้ำได้ผลเดียวกัน (ขั้น 6)
- เรื่องที่ผู้ใช้ต้องตัดสินเสมอ: เปลี่ยน spec/contract, ขยาย/ลด scope, เพิ่ม dependency, แตะ schema หรือข้อมูลที่ใช้ร่วมกัน, รันบน env จริง, commit, push · subagent เขียน decision request (`.agents/templates/decision-request.md`) ใส่ในรายงานถึง lead แล้วหยุดส่วนที่รอคำตอบ
- role ไม่คุยกันเอง: รายละเอียด contract ที่อีก role ต้องใช้ ใส่ในรายงานถึง lead แล้ว lead ใส่ใน brief ของขั้นถัดไป ความเห็นตรงกันของ subagent ไม่นับเป็นการตัดสินใจ
- **ไม่ใช้ shared task list:** ticket คือ checklist ของงาน ประสานงานด้วย brief และรายงาน (workflow นี้เป็นลำดับตายตัวที่ทุกขั้นมีเจ้าของชัด) — ทบทวนเมื่อรันหลายงานอิสระพร้อมกัน
- **lead สรุปสถานะให้ผู้ใช้หลังจบแต่ละขั้น:** ขั้นไหนเสร็จ รอผลจากใคร ติดอะไร (ตารางสั้น) และเขียนตารางเดียวกันทับลง `progress.md`
- หลัง qa รันเสร็จ (ใน spawn เดียวกับการรัน) qa เขียนผลของรอบนั้นพร้อมสรุปเคสสำหรับ manual test (ภาษาไทย: ทดสอบอะไร / request / response จริง / ผล / curl ให้ลองเอง) ที่ `.scratch/<feature-slug>/reviews/<ticket>/r<n>/qa.md` (slug = โฟลเดอร์ของไฟล์ ticket) — รูปแบบอยู่ใน `.claude/agents/qa.md` หัวข้อ "Evidence for each run" · lead ระบุโฟลเดอร์ของรอบใน brief และลิงก์ไฟล์ใน `evidence.md`
- ทุกคนพูดภาษาไทยเป็นค่าเริ่มต้น (path / คำสั่ง / โค้ดคงเดิม)
- ห้ามรัน `Regression` ทั้งชุด รันเฉพาะโฟลเดอร์ของ ticket · ห้ามพิมพ์ secret · ห้าม commit/push โดย subagent

## เมื่อเครื่องมือหรือสภาพแวดล้อมล้ม (retry ตามประเภท)
กฎ "ไม่เกิน 3 รอบต่อประเด็น" ใช้กับโค้ดที่ผิด ส่วนนี้ใช้เมื่อ**สภาพแวดล้อม**ล้ม ซึ่งไม่นับเป็นรอบ subagent ทำตามตารางนี้ แล้วรายงานประเภทกับจำนวนครั้งให้ lead lead บันทึกลง `log.tsv`

| ประเภท | ตัวอย่าง | ทำอย่างไร |
|---|---|---|
| network / DB ต่อไม่ได้ | `read EADDRNOTAVAIL`, connection refused | `SELECT 1` หรือเช็คการเชื่อมต่อ แล้ว retry **ครั้งเดียว** |
| โควตาหรือ rate limit | OTP generate เกิน 5 ครั้ง / 5 นาที / identifier | **ห้ามรันซ้ำทันที** รายงาน `BLOCKED` พร้อมเวลาที่รันได้อีก lead spawn qa ใหม่หลังเวลานั้น (subagent รอเองด้วย `sleep` ไม่ได้) |
| server ไม่ขึ้น / port ชน / tool error | `address already in use`, binary เก่า | เปลี่ยนวิธี **หนึ่งครั้ง** เช่น หยุด process เก่าของตัวเองแล้วเริ่มใหม่ ห้ามฆ่า process ที่ตัวเองไม่ได้เปิด |
| เกินเวลา / output ใหญ่เกิน | รันทั้งโฟลเดอร์นานผิดปกติ | ลด scope เช่น รันเฉพาะ request ที่ fail แล้วรายงานว่าลดอะไร |
| ไม่แน่ใจว่าเป็นประเภทไหน | | รายงาน `BLOCKED` พร้อม log ห้ามเดา |

- **ล้มแบบเดิม 2 ครั้ง = หยุด:** subagent รายงาน `BLOCKED` พร้อม path ของ log lead เขียนสมมติฐานที่ทั้งสองครั้งใช้ร่วมกันลง `log.tsv` แล้วถามผู้ใช้ ห้ามสั่ง retry แบบเดิมเป็นครั้งที่ 3
- **subagent ที่ติดหรือวน** (รายงานว่ายังไม่เสร็จ, ทำไม่ตรง brief, หรือรันคำสั่งเดิมซ้ำโดยไม่คืบหน้า): lead ไม่สั่งซ้ำ ให้ spawn **ตัวใหม่** พร้อม brief เดิม + คำสั่งที่เพิ่มทีหลัง + path รายงานของตัวก่อน ถ้าตัวใหม่ติดที่เดิมอีก แปลว่าเป็นทางตัน ให้ถามผู้ใช้

## กติกาการประสานงานของ lead (บทเรียน ticket 47 — ปรับเป็นแบบ subagent)
1. **รอคำตัดสินก่อน spawn งานที่ขึ้นกับมัน** — เมื่อรายงานใดมี decision request ห้าม spawn ขั้นที่งานขึ้นกับคำตัดสินนั้น (แทน "HOLD") งานที่ไม่เกี่ยวเดินต่อได้ · ถ้ามี subagent แบบ background ที่ขึ้นกับเรื่องนั้นกำลังทำอยู่ ให้รอผลแล้วถือว่าผลนั้นต้องตรวจใหม่หลังได้คำตัดสิน ห้าม spawn qa (รัน) จนกว่าจะได้คำตัดสิน
2. **ถามให้ครบก่อนส่งงาน** — ก่อน spawn ขั้นที่ทำตามคำตัดสินของผู้ใช้ ตรวจว่ามี fix list / ข้อเสนอของ reviewer ค้างที่เกี่ยวกับเรื่องเดียวกันหรือไม่ แล้วรวมถามในรอบเดียว (ไม่ส่งงานตามตัวเลือกแรกแล้วแก้ซ้ำทีหลัง)
3. **brief ใช้คำตัดสินล่าสุดเท่านั้น** — เมื่อผู้ใช้เปลี่ยนคำตัดสิน brief ถัดไปใส่คำตัดสินใหม่แบบคำต่อคำ และเขียนว่า "แทนที่คำตัดสิน <เรื่อง> ก่อนหน้า" ไม่ใส่คำตัดสินเก่าที่ถูกแทนแล้ว
4. **ยืนยันผลก่อนบอกทีมว่าเสร็จ** — งานที่ lead ลงมือเอง (เช่น แก้ env ของ local) ต้องตรวจผลจริง (grep / อ่านไฟล์) ก่อนเขียนลง brief · ไฟล์ env อาจเป็น symlink (ดู skill `local-run`)
5. **แก้หลัง review ต้องไม่หลุดการตรวจ** — ถ้ามีการแก้ไฟล์ (รวม Bruno) หลัง reviewer รอบล่าสุด ให้ spawn reviewer ตรวจ delta ก่อนปิดงาน หรือบันทึกใน `## Comments` ของ ticket ว่าส่วนนั้นไม่ได้ผ่านการตรวจ
6. **การรัน local มีจุดเริ่มเดียว** — qa รัน server / `bru` ได้เฉพาะใน spawn ที่ brief เขียนว่า `Step: 4 run` spawn ที่เขียนหรือเทียบ contract ห้ามรัน (แทนสัญญาณ "GO")
7. **ผลจาก subagent แบบ background มาถึงไม่พร้อมกัน** — lead รอจนได้ผลของทุกขั้นที่ขั้นถัดไปต้องใช้ ไม่ spawn ซ้ำเพราะยังไม่ได้ผล และไม่เดาผลที่ยังไม่มา (แทนข้อ idle notification)
8. **ตรวจโค้ด/config ก่อนเขียน contract หรือค่า env ใน brief** (บทเรียน ticket 48, 03) — ทุกข้อที่อ้างพฤติกรรมของ endpoint/middleware อื่น (เช่น "โหมด cookie ปิด → 403", "pre-sign เดิมไม่เรียก account") หรือบอกว่า env ตัวไหนตั้งที่ server ไหน ให้ตรวจด้วย grep / อ่านโค้ดแล้วใส่ `file:line` ใน brief ก่อนส่ง · env ใช้ตาราง "env ตัวไหนอ่านที่ server ไหน" ใน `.claude/skills/local-run/SKILL.md` (ตัวที่ไม่อยู่ในตาราง → grep หาที่ใช้จริงก่อนตั้ง) · เมื่อรายงานของ subagent ท้วง contract ของ lead ให้ตรวจหลักฐานเองแล้วแก้ใน brief ถัดไปด้วยข้อความ "แทนที่คำสั่ง ... ก่อนหน้า" (ข้อ 3) และบอกผู้ใช้ตรงๆ ว่า lead สั่งผิดตรงไหน

## ทำต่อเมื่อ session หลุด
subagent จบทุกขั้นอยู่แล้ว สิ่งที่หายไปเมื่อ session หลุดจึงมีแค่ความจำของ lead กับ subagent แบบ background ที่ยังไม่ส่งผล session ใหม่ทำแบบนี้
1. อ่าน `reviews/<ticket>/progress.md` และ `log.tsv` **ก่อน** ห้ามใช้ความจำหรือสรุปจากแชตเก่า
2. ตรวจกับของจริง: `git status --short` + `git diff --stat` เทียบกับ `git-status.txt` ของรอบล่าสุด และเช็คว่าไฟล์หลักฐานที่ `progress.md` อ้างถึงมีอยู่จริง
3. ถือว่าผล PASS ของรอบก่อนเป็น**คำกล่าวอ้าง**จนกว่าจะตรวจแล้วว่าโค้ดไม่เปลี่ยน ถ้าโค้ดเปลี่ยน ขั้นที่ตรวจไปแล้วต้องตรวจใหม่
4. **ห้ามทำซ้ำขั้นที่เสร็จและโค้ดไม่เปลี่ยน** ขั้นที่ `progress.md` บอกว่ากำลังทำ (subagent ที่หายไปพร้อม session) ให้ spawn ใหม่ และถ้ามีไฟล์ที่แก้ค้างครึ่งทาง ให้ backend ตัวใหม่อ่าน `git diff` ก่อนเริ่ม
5. บอกผู้ใช้ว่าทำต่อจากขั้นไหน และพบอะไรเปลี่ยนไปบ้าง แล้วเขียนแถว `resume` ลง `log.tsv`
